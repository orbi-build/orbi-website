Orbi 是一个开源系统，把 GitHub Issue 从实现、评审一路做到合并和发版。这篇写给让编程 agent 写代码和测试、再靠测试放行合并的工程负责人和独立开发者。读完可以用这次审查的分类方法和仓库规则检查自己的测试，也能看到初始化、并行度的本地对照，以及 CI 前后样本的耗时变化。

我是 Larry 🍀 Orbi，Orbi 的创始人。

这次我审查的是 Orbi Cloud 自己的 Vitest 测试集，测试注册行大多最后由 Orbi 的交付机器人修改。

## 这次审查怎么算

2026 年 11 月 18 日，我让相互独立、只读的 Codex 会话，对 Orbi Cloud 仓库 beta 分支上提交 `4619a9fc` 的测试逐条分类。范围是 Vitest 运行的 3 组 TypeScript 测试：主测试目录、浏览器测试和运维脚本测试。仓库里的 5 个 Python 测试文件、32 个测试方法没有纳入。orbi-cloud 仓库是私有的，文中只引用审查数据、写出 Issue 编号，不放链接。每条分类和计数脚本都保存在内部讨论中。

计数按展开后的测试用例算。代码里用参数化方式或循环注册的测试，都会展开计数；如果循环写在测试体内，检查多个输入，仍算 1 条用例。同一条用例只要同时含有行为断言和实现断言，就归为依赖实现细节。下文的实现断言子类可以重叠。

从数据库读取业务记录、检查发给外部服务的内容，都算行为测试；用选择器提取可见文字也算。判断的关键是：用户或调用方看到的结果可以不变时，这条断言会不会因为实现方式变了就失败。

我抽查了 5 处源码，只有一处有歧义：它按表单提交地址统计禁用控件的数量。用这个地址来识别页面上渲染出的控件，也有合理性。这点抽查不足以推算整次审查的分类错误率。这是一次静态审查，没有测缺陷检出能力，也没有测每条测试失败后要花多少代价处理。

为了复核分类，我从主测试目录随机抽了 60 条测试注册，随机种子为 `20261120`，交给一个独立的 DeepSeek 会话。它拿到相同的分类定义，但看不到原审查的标签。两次分类有 48 条一致，一致率为 80%，分类一致性指标 Cohen's kappa 为 0.60。

原审查判为依赖实现的 18 条，它全部同意；12 条分歧的方向也相同：原审查判为行为，它判为依赖实现，主要涉及对隐藏输入等 HTML 片段的精确比较，以及直接调用内部辅助函数。就这份样本看，复核没有显示原审查高估了依赖实现的数量。此前的一次尝试已作废，因为那个会话找到了存放原审查标签的文件，并读了它。

## AI 写的测试里，有多少在测实现

在清理前的提交 `4619a9fc` 上，按严格口径，5,087 条用例中有 1,739 条依赖实现细节，占 34%。这里也包含辅助函数引入的源码检查，以及部分有歧义的元素定位方式，下文会分开说明。总数里还包含 16 条存疑用例，它们没有计入这 1,739 条。

| 测试目录 | 文件数 | 用例数 | 依赖实现细节 | 存疑 |
|---|---:|---:|---:|---:|
| 主目录 `test/` | 160 | 3,999 | 1,046 | 7 |
| `test/browser/` | 80 | 639 | 466 | 0 |
| `test/runbook/` | 47 | 449 | 227 | 9 |

下面列的是审查中「测实现细节」的具体类别。同一条用例可以出现在多个类别中，所以不能把同一组测试的各行相加，否则会重复计数。

| 断言类别 | 主测试 | 浏览器测试 | 运维脚本测试 |
|---|---:|---:|---:|
| 读取源码文本 | 15 | 360 | 112 |
| 内部调用的参数或次数 | 47 | 1 | 49 |
| SQL 文本 | 31 | 0 | 4 |
| 内部结构：class、ID、数组长度、脚本文本、HTML 结构 | 939 | 221 | 73 |
| 固定内部结构的快照 | 18 | 0 | 0 |
| 调用内部辅助函数，检查中间值 | 74 | 0 | 57 |

浏览器测试中有 244 条入选，唯一原因是挂载页面的辅助函数在运行页面脚本前，会先查找脚本中的源码标记。它们符合严格定义。这个辅助函数在各文件里各有一份副本，72 个浏览器测试文件定义了自己的 `mount`，修复时需要逐个文件改成让页面自行运行脚本。另有一些归入「内部结构」的用例，用 class 名定位元素，或统计用户能点击的控件数量，这些分类也有商榷空间。

把仅由挂载函数引入的源码检查，以及这些有歧义的定位方式排除后，可以得到更窄的口径。按这个口径，审查估计有约 1,300–1,500 条用例明确依赖实现，占 25%–30%。这是近似重分类，没有再逐条精确统计，也没有统计置信区间。完整报告保留 34% 作为严格口径的结果；多条用例可以按同一种方式修复，并不影响这个计数成立。

## 这些测试是谁写的

`git blame` 显示，4,687 行测试注册中，3,576 行的最后修改者是 `orbi-build[bot]`，四舍五入到整数百分比是 76%。这里统计的是注册行的最后修改者，无法据此还原每一条断言最初由谁写成。一次参数化注册可以对应多条用例，所以这里的分母与审查的 5,087 条不同。

这能说明，这套测试主要由机器人维护。我没有一组人写的测试作对照，也没有把相同任务分别交给人和 agent 比较。这次审查无法证明 agent 写的测试比人差。如果你已经让 AI 写单元测试，也要把浏览器和运维脚本测试一起纳入检查。

## 为什么会写出这些实现断言

我自己的写票规则，曾要求把验收标准写成「只存在一个渲染或判断函数」。具体票面也要求过某句旧文案「在源码里搜不到」。交付 agent 按字面执行了这些要求，原本清理架构的要求，就成了长期检查源码组织方式的测试。

Issue #3355 要求首屏和轮询响应共用计费逻辑，验收项中包含：源码里只保留一份免费运行次数的实现。Issue #3436 要求旧文案从源码中消失。它对应的 `proof-receipt-source-3436.test.ts` 会递归扫描 `src` 下的每个 `.ts` 文件，查找那句旧文案。通过这条测试，只能证明这些文件里没有这句话，无法证明访客在页面上看到了什么。

Cloud 状态页的主卡片，既有可读的文本样本，也有整页 SHA-256 快照。哈希还覆盖了页面其他部分，因此下面的更新数量无法说明每次更新是否值得，也无法说明快照抓住了多少缺陷。

这个快照存在了约 8 天，从 2026 年 11 月 11 日 02:24（北京时间）到 11 月 19 日 12:50（北京时间）。期间有 36 个非合并提交改过 `page-sha256.json`，最后修改者全是机器人：1 次创建，35 次重写。35 次重写中，28 次没有改动主卡片的任何文本样本，7 次有意修改了主卡片。测试注释也记下了多次重建：主卡片文字逐字未变，整页哈希却变了。

我修改了[写任务请求的方法](/zh/blog/write-a-request/)，因为要求 agent 保留这些实现检查的，正是我自己的验收措辞。

## 我给仓库加了什么规则

2026 年 11 月 18 日，我在提交 `62738cff` 中给 `AGENTS.md` 加了这条规则。中文原文如下：

> 测试只断言用户或调用方看得到的结果：接口返回、页面上的文字和链接、发出去的邮件和 GitHub 评论、库里代表业务事实的记录、脚本的退出码和输出。下面这些不写，票面要求也不写（票面写了，在合并请求里说明改成了哪个可见结果）：读源码文本（搜某字符串在不在、数规则条数、断言只有一份实现）；页面脚本或 SQL 语句的写法；内部函数的调用参数和次数（对外发送的内容除外）；内部数组长度、常量值、元素 id；整页哈希快照。2026-11-18 全仓审查，这几类约占全部用例的三成，改个名、调个样式就红，还拖慢每轮测试。

测试要求到「整页哈希快照」为止，后面记录的是这次审查的背景。其中的「三成」，对应较窄口径的取整估计；严格口径是 34%。「拖慢每轮测试」是这条规则提出的理由，审查并没有单独测量这些断言类别的运行成本。下面的耗时测量，针对的是迁移初始化和并行度。

写票规则也随之改了：同样的数据，两处要显示同样的结果，在渲染后的页面或 API 响应上检查。要求「只存在一份实现」，就把代码组织方式写进了合并条件。评审者可以检查逻辑有没有共用，不必把这种结构变成永久断言。

## 清理做到了哪里

11 月 19 日 09:54（北京时间），我开了 6 张清理票，编号为 #3536 至 #3541。Orbi 创建并合并了对应的全部 6 个 PR（拉取请求），最后一个在 11 月 20 日 08:15（北京时间）合并。

清理涉及浏览器脚本挂载、整页快照、源码文本扫描、页面渲染断言和运维脚本测试。快照那张票，把整页哈希换成了对相关状态下标题、按钮和链接的断言。浏览器测试则让页面运行自己的脚本，不再按源码标记挑出脚本、再注入执行。

Issue #3539 是一次还不彻底的改进。suggestion-block 测试以前断言返回的 HTML 含有 `location.reload()`。改写后，断言的对象换成了空状态和有内容时的按钮文字，以及正在读取建议时没有按钮。这样刷新方式可以改，预期显示的控件不用跟着改。这条测试只覆盖渲染出的控件；点击之后有没有发请求、页面有没有变化，还需要浏览器断言。

但改写后仍留着 `expect(SUGGESTION_RERUN_QUERY).toBe(SUGGESTION_RERUN_PATH)`，它断言两个常量相等，违反了新规则。所以我不能说这次清理已经完全符合规则。即使交付提示词里已经带上规则，仍然需要评审者检查具体断言。

## 测试还可以怎样跑得更快

这一部分适用于 Cloudflare Workers + Vitest，依赖版本为 `@cloudflare/vitest-plugin` 1.x 和 Vitest 4。运行耗时的调整与断言清理分开进行。Issue #3493 测了初始化和并行度，其中对断言的修改仅限于移除一条多余的计时检查。

原先，各测试文件初始化数据库时，都会从 `cloudflare:test` 导入 `applyD1Migrations`。单文件测量时，仅加上这个导入，初始化就要花 1.78 秒。去掉导入，直接对 `env.DB` 执行相同逻辑，跑完全部 86 个迁移约需 0.06 秒。光加载库的耗时，就超过了直接执行迁移。

替代代码放在 `test/apply-migrations.ts`，仍保留相同的 4 步：创建迁移记录表、读取已执行的迁移名、跳过已执行的迁移，再把每个剩余迁移与它的记录一起批量执行。准备好记录表和记录用的语句后，循环如下：

```typescript
for (const migration of env.TEST_MIGRATIONS) {
	if (applied.has(migration.name)) continue;
	const queries = migration.queries.map((query) => env.DB.prepare(query));
	queries.push(recordApplied.bind(migration.name));
	await env.DB.batch(queries);
}
```

#3493 的本地测量都在同一台 32 核机器上完成，开启了覆盖率：

| 配置 | 并行 worker 数 | 总耗时 | 累计初始化耗时 |
|---|---:|---:|---:|
| 原配置 | 2 | 199 秒 | 214 秒 |
| 只把迁移初始化逻辑内联 | 2 | 156 秒 | 8 秒 |
| 只提高并行度 | 8 | 93 秒 | 402 秒 |
| 两项都改 | 8 | 69 秒 | 10 秒 |

累计初始化耗时，加的是各文件、各 worker 上花的时间，因此可以超过总耗时。只提高并行度那次，整轮更快结束，累计初始化耗时却更多。只看总耗时，就会漏掉重复导入的成本。

现在 CI 设置 `VITEST_MAX_WORKERS=8`，交付沙箱仍保留默认值 2。开到 8 个 worker 后，一条请求耗时断言失败了，报错是 `expected 2216 to be less than 2000`。这条测试原本就用一个可控的阻塞点拦住数据库写入，先收到响应，再放行写入。这个顺序已经能证明响应没有等待写入。我移除了多余的耗时断言，没有把阈值调大。

GitHub Actions 的 `Run npm test` 步骤，在改动前的 60 次成功 PR 运行中，耗时中位数为 271 秒。这批运行都发生在 2026 年 11 月 18 日，按 UTC 计；查询原本覆盖 11 月 17–18 日，但返回结果达到 60 条上限，全部来自 18 日。改动后的样本有 80 次成功 PR 运行，中位数为 102 秒。这里量的是测试步骤的耗时，包含测试命令本身的额外开销，不代表整个工作流的耗时；改动前的样本也没有覆盖当天全部运行。

改动后的样本窗口为 2026 年 11 月 19 日 15:40 UTC 至 11 月 20 日 00:46 UTC。两批样本之间仓库仍在变化，其中也有测试清理。因此，CI 数据呈现的是一次前后对比；上面的本地表格才把初始化和并行度的影响分开。两个提速 PR #3527、#3533，分别在 11 月 19 日 08:36 和 10:42（北京时间）合并，都早于改动后的样本窗口。

## 检查自己仓库时可以照着做

- 按断言实际检查的内容分类；一条用例混有多种断言、或分类存疑时，明确记下来。
- 先看共用的测试辅助函数，再判断每条被标记的用例是否需要单独修复。
- 遇到源码扫描和实现断言，回查是哪张任务票要求这么写的。
- 验收围绕「相同输入下能看到什么结果」来写，评审时再对照这个要求检查断言。
- 把范围过大的快照换成真正要保留的输出；按钮点击后实际做了什么，仍要保留交互检查。
- 分开测初始化和执行耗时，在同一台机器上比较并行度；能控制执行顺序时，优先用顺序断言代替实际耗时断言。
