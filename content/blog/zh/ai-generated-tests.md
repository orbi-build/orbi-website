Orbi 是一个开源系统，把 GitHub Issue 从实现、评审一路做到合并和发版；这次审查的是它的托管服务 Orbi Cloud 的私有仓库。这篇写给让编程 agent 写代码和测试、再靠测试放行合并的工程负责人和独立开发者。你可以拿这次审查的分类方法和仓库规则检查自己的测试。我也比较了数据库迁移初始化和并行度的本地测量结果，以及 CI 改动前后两批样本的耗时。

我是 Larry 🍀 Orbi，Orbi 的创始人。

我这次审查了 Orbi Cloud 自己的 Vitest 测试集，其中大多数测试注册行最后由 Orbi 的交付机器人修改。

## 这次审查怎么算

2026 年 11 月 18 日，我让相互独立、只读的 Codex 会话对 Orbi Cloud 仓库 beta 分支上提交 `4619a9fc` 的测试逐条分类。审查覆盖 Vitest 运行的 3 组 TypeScript 测试：主测试目录、浏览器测试和运维脚本测试。仓库里的 5 个 Python 测试文件、32 个测试方法没有纳入。orbi-cloud 仓库是私有的，我只引用审查数据、写出 Issue 编号，不放链接。每条分类和计数脚本都保存在内部讨论中。

参数化或循环注册的测试，按展开后的用例数计数；循环如果写在测试体内，即使检查多个输入，仍算 1 条用例。同一条用例只要同时含有行为断言和实现断言，就归为依赖实现细节。实现断言的子类可以重叠。

从数据库读取业务记录、检查发给外部服务的内容，都算行为测试；用选择器提取可见文字也算。我判断的是：用户或调用方看到的结果没变，只改实现方式，这条断言会不会失败？

我抽查了 5 处源码，只有一处有歧义：它按表单提交地址统计禁用控件的数量，用这个地址识别页面上的控件也说得通。抽查太少，无法估计整次审查的分类错误率。我只读了测试源码，没有测它们能发现多少缺陷，也没有测每条测试失败后要花多少代价处理。

我从主测试目录随机抽了 60 条测试注册，随机种子为 `20261120`，交给一个独立的 DeepSeek 会话复核。它拿到相同的分类定义，但看不到原审查的标签。两次分类有 48 条一致，一致率为 80%，分类一致性指标 Cohen's kappa 为 0.60（通常算中等一致）。

原审查判为依赖实现的 18 条，它全部同意。12 条分歧中，原审查都判为行为，它都判为依赖实现；主要涉及精确比较隐藏输入等 HTML 片段，以及直接调用内部辅助函数。在这份主目录样本上，复核比原审查更严，没有把原审查判为依赖实现的用例改判成行为，所以在这份样本里看不出原审查高估。第一次复核作废了，因为那个会话找到了存放原审查标签的文件，并读了它。

## AI 写的测试里，有多少在测实现

清理前的提交 `4619a9fc` 中，按严格口径，5,087 条用例有 1,739 条依赖实现细节，占 34%。其中包含辅助函数引入的源码检查，以及部分有歧义的元素定位方式，后面会分开说明。总数还包含 16 条存疑用例，没有计入这 1,739 条。

| 测试目录 | 文件数 | 用例数 | 依赖实现细节 | 存疑 |
|---|---:|---:|---:|---:|
| 主目录 `test/` | 160 | 3,999 | 1,046 | 7 |
| `test/browser/` | 80 | 639 | 466 | 0 |
| `test/runbook/` | 47 | 449 | 227 | 9 |

审查把实现断言分成以下类别。同一条用例可以属于多个类别，把同一组测试的各行相加会重复计数。

| 断言类别 | 主测试 | 浏览器测试 | 运维脚本测试（`test/runbook/`） |
|---|---:|---:|---:|
| 读取源码文本 | 15 | 360 | 112 |
| 内部调用的参数或次数 | 47 | 1 | 49 |
| SQL 文本 | 31 | 0 | 4 |
| 内部结构：class、ID、数组长度、脚本文本、HTML 结构 | 939 | 221 | 73 |
| 固定内部结构的快照 | 18 | 0 | 0 |
| 调用内部辅助函数，检查中间值 | 74 | 0 | 57 |

浏览器测试中有 244 条符合严格定义，唯一原因是挂载页面的辅助函数在运行页面脚本前，会先查找脚本中的源码标记。这些辅助函数是各文件自带的副本，72 个浏览器测试文件各自定义了 `mount`，修复时要逐个文件改成让页面自己运行脚本。还有一些归入「内部结构」的用例，用 class 名定位元素，或统计用户能点击的控件数量；这些分类也有商榷空间。

排除仅由挂载函数引入的源码检查和有歧义的定位方式后，按更窄的口径，审查估计约有 1,300–1,500 条用例明确依赖实现，占 25%–30%。这个估计没有再逐条精确计数，也没有统计置信区间。完整报告仍保留严格口径的 34%；多条用例能用同一种方式修复，不影响这个计数。

## 这些测试是谁写的

`git blame` 显示，4,687 行测试注册中，3,576 行最后由 `orbi-build[bot]` 修改，四舍五入到整数百分比是 76%。它只能告诉我谁最后改了注册行，无法还原每条断言最初由谁写成。一次参数化注册可以对应多条用例，所以这里的分母与审查的 5,087 条不同。

这套测试主要由机器人维护，但我没有一组人写的测试作对照，也没有把相同任务分别交给人和 agent 比较，无法据此判断 agent 写的测试比人差。如果你已经让 AI 写单元测试，别只查主目录：按用例占比，这次依赖实现最集中的是浏览器和运维脚本测试。

## 为什么会写出这些实现断言

我自己的写票规则曾要求把验收标准写成「只存在一个渲染或判断函数」，具体票面也要求过某句旧文案「在源码里搜不到」。交付 agent 照着做了，把清理架构的要求变成了长期检查源码组织方式的测试。

Issue #3355 要求首屏和轮询响应共用计费逻辑，验收项要求源码里只保留一份免费运行次数的实现。Issue #3436 要求旧文案从源码中消失，对应的 `proof-receipt-source-3436.test.ts` 会递归扫描 `src` 下的每个 `.ts` 文件，查找那句旧文案。测试通过只能证明这些文件里没有这句话，无法证明访客在页面上看到了什么。

Cloud 状态页主卡片的测试用了可读的文本样本，也用了整页 SHA-256 快照。因为哈希覆盖整页，下面的重写次数既说明不了每次更新是否必要，也说明不了快照抓到了多少缺陷。

这个快照存在了约 8 天，从 2026 年 11 月 11 日 02:24（北京时间）到 11 月 19 日 12:50（北京时间）。期间有 36 个非合并提交改过 `page-sha256.json`，最后修改者全是机器人：1 次创建，35 次重写。35 次重写中，28 次没有改动主卡片的任何文本样本，7 次有意修改了主卡片。测试注释也记下了多次重建：主卡片文字逐字未变，整页哈希却变了。

是我自己的验收措辞让 agent 写出了这些实现检查，所以我修改了[写任务请求的方法](/zh/blog/write-a-request/)。

## 我给仓库加了什么规则

2026 年 11 月 18 日，我在提交 `62738cff` 中给 `AGENTS.md` 加了这条规则。规则原文如下：

> 测试只断言用户或调用方看得到的结果：接口返回、页面上的文字和链接、发出去的邮件和 GitHub 评论、库里代表业务事实的记录、脚本的退出码和输出。下面这些不写，票面要求也不写（票面写了，在合并请求里说明改成了哪个可见结果）：读源码文本（搜某字符串在不在、数规则条数、断言只有一份实现）；页面脚本或 SQL 语句的写法；内部函数的调用参数和次数（对外发送的内容除外）；内部数组长度、常量值、元素 id；整页哈希快照。2026-11-18 全仓审查，这几类约占全部用例的三成，改个名、调个样式就红，还拖慢每轮测试。

测试要求到「整页哈希快照」为止，后面是这次审查的背景。「三成」是较窄口径的取整估计；严格口径是 34%。我把「拖慢每轮测试」作为加这条规则的理由，但审查没有单独测量这些断言类别的运行成本。下面只测了迁移初始化和并行度。

我也改了写票规则：同样的数据，两处要显示同样的结果，在渲染后的页面或 API 响应上检查。要求「只存在一份实现」，就把代码组织方式写进了合并条件。评审者可以检查逻辑有没有共用，不必为这种结构加永久断言。

## 清理做到了哪里

11 月 19 日 09:54（北京时间），我开了 6 张清理票，编号为 #3536 至 #3541。Orbi 创建并合并了对应的全部 6 个 PR（拉取请求），最后一个在 11 月 20 日 08:15（北京时间）合并。

清理涉及浏览器脚本挂载、整页快照、源码文本扫描、页面渲染断言和运维脚本测试。快照那张票不再检查整页哈希，改为检查相关状态下的标题、按钮和链接。浏览器测试让页面运行自己的脚本，不再按源码标记挑出脚本、再注入执行。

Issue #3539 中，suggestion-block 测试以前断言返回的 HTML 含有 `location.reload()`。改写后，测试检查空状态和有内容时的按钮文字，并断言读取建议时没有按钮。刷新方式可以改，预期显示的控件不用跟着改。测试只覆盖渲染出的控件；点击之后有没有发请求、页面有没有变化，仍需要浏览器断言。

改写后仍留着 `expect(SUGGESTION_RERUN_QUERY).toBe(SUGGESTION_RERUN_PATH)`，检查两个常量是否相等，违反了新规则。这次清理还没完全符合规则；即使交付提示词里写了规则，评审者仍要检查具体断言。

## 测试还可以怎样跑得更快

耗时调整适用于 Cloudflare Workers + Vitest，依赖版本为 `@cloudflare/vitest-plugin` 1.x 和 Vitest 4。运行耗时的调整和断言清理分开做。Issue #3493 测了初始化和并行度，只改了一处断言：移除一条多余的计时检查。

原先，各测试文件初始化数据库时，都会从 `cloudflare:test` 导入 `applyD1Migrations`。在单个文件上测，仅这个导入就让初始化多花 1.78 秒。去掉导入，直接对 `env.DB` 执行相同逻辑，跑完全部 86 个迁移约需 0.06 秒。

替代代码放在 `test/apply-migrations.ts`，仍按原来的 4 步执行：创建迁移记录表、读取已执行的迁移名、跳过已执行的迁移，再把每个剩余迁移与它的记录一起批量执行。`recordApplied` 是一条 D1 预编译语句，它的 `.bind()` 把迁移名填进 `?` 占位符，不是 JavaScript 函数的 `bind`。下面是循环前的那条语句和循环本身：

```typescript
const recordApplied = env.DB.prepare(`INSERT INTO ${MIGRATIONS_TABLE} (name) VALUES (?);`);

for (const migration of env.TEST_MIGRATIONS) {
	if (applied.has(migration.name)) continue;
	const queries = migration.queries.map((query) => env.DB.prepare(query));
	queries.push(recordApplied.bind(migration.name));
	await env.DB.batch(queries);
}
```

#3493 的本地测量都在同一台 32 核机器上完成，开启了覆盖率：

| 配置 | 并行 worker 数 | 总耗时 | 累计初始化耗时 |
|---|---:|---:|---:|
| 原配置 | 2 | 199 秒 | 214 秒 |
| 只把迁移初始化逻辑内联 | 2 | 156 秒 | 8 秒 |
| 只提高并行度 | 8 | 93 秒 | 402 秒 |
| 两项都改 | 8 | 69 秒 | 10 秒 |

累计初始化耗时把各文件、各 worker 花的时间相加，所以可以超过总耗时。只提高并行度那次，整轮更快结束，累计初始化耗时却更多。只看总耗时，会漏掉重复导入的成本。

现在 CI 设置 `VITEST_MAX_WORKERS=8`，交付沙箱仍保留默认值 2。开到 8 个 worker 后，一条请求耗时断言失败，报错是 `expected 2216 to be less than 2000`（单位是毫秒，上限 2 秒）。测试原本就用可控的阻塞点拦住数据库写入，收到响应后再放行，已经能证明响应没有等待写入。我移除了多余的耗时断言，没有把阈值调大。

改动前，GitHub Actions 的 `Run npm test` 步骤在查询窗口里最近 60 次成功 PR 运行中，耗时中位数为 271 秒。这批运行都发生在 2026 年 11 月 18 日，按 UTC 计。查询覆盖 11 月 17–18 日，但返回结果达到 60 条上限，全部来自 18 日，没有覆盖当天全部运行。改动后取最近 80 次成功 PR 运行，中位数为 102 秒。这期间测试并没有变少：测试注册行从审查提交上的 4,687 行，增加到 11 月 20 日 00:53 UTC（改动后样本刚结束）beta 上的 4,952 行。两批样本记录的都是测试步骤的耗时，包含测试命令本身的额外开销，不代表整个工作流的耗时。

改动后的样本窗口为 2026 年 11 月 19 日 15:40 UTC 至 11 月 20 日 00:46 UTC。两批样本之间仓库仍在变化；测试清理也和改动后的样本窗口重叠，最后一个清理 PR 在 11 月 20 日 00:15 UTC 合并。CI 数据只能用来比较改动前后的耗时；上面的本地表格把初始化和并行度的影响分开测了。两个提速 PR #3527、#3533，分别在 11 月 19 日 08:36 和 10:42（北京时间）合并，都早于改动后的样本窗口。

## 检查自己仓库时可以照着做

- 按断言实际检查的内容分类；同一条用例混有多种断言，或分类存疑时，都记下来。
- 先看共用的测试辅助函数，再判断每条被标记的用例是否需要单独修复。
- 遇到源码扫描和实现断言，回查是哪张任务票要求这么写的。
- 验收写清「相同输入下能看到什么结果」，评审时对照这个要求检查断言。
- 把范围过大的快照换成真正要保留的输出；按钮点击后实际做了什么，仍要保留交互检查。
- 分开测初始化和执行耗时，在同一台机器上比较并行度；能控制执行顺序时，优先用顺序断言代替实际耗时断言。
