在 Orbi Cloud 上连接一个 GitHub 仓库，页面会显示「正在准备工作环境」。这次上线之前，这个页面可能要停一分多钟：生产环境里有一次连接，从点「连接」到页面显示就绪用了 79 秒。现在测试环境上是 11.5 到 14.6 秒；生产跑的是同一份代码，但我们还没在生产上量过。机器没换。最大的改动是不让新用户排在一个后台任务后面：主机改用长轮询等新请求，不再每分钟查一次，循环交给 systemd。

我是 Lawrence Liu，Orbi 的创始人。Orbi 接一张打了 `ai-ready` 标签的 GitHub Issue，用它的编程 agent Pi 写代码，另开一个会话评审，合并，再发版。这次改动一共 32 张票，其中 31 张在 Orbi 自己的仓库上走完了这条流程，从 10 月 10 日夜里到 11 日深夜。下面是完整的工程记录：怎么量、为什么瓶颈在排队、四版越改越小的方案，还有一个审查方提醒过、我们还是带上线的竞态。文中时间都是新加坡时间（UTC+8）。

## 先说结论

1. **页面还在显示「准备中」，人就走了。** 有一次环境其实已经好了，页面每 10 秒才查一次，还没来得及显示，用户就离开了。
2. **慢的不是机器，是排队。** 开通本身 31 到 50 秒。在这之前，请求要等 3 到 41 秒才被主机看到，最长的一次等了 110 秒，因为每分钟一轮的任务要先把所有老沙箱刷新一遍，才轮到看新用户。
3. **把定时器调快也没用。** 那时一轮已经接着一轮在跑，每一轮还是先刷新全部。
4. **最后用的是长轮询。** 主机向 Cloud 要新请求，Cloud 把这个请求挂住最多 20 秒，每秒查一次。现在认领只要 1 到 2 秒。GitHub 的自托管执行器也是这么和 GitHub 通信的。
5. **定稿只是给现有脚本加了一个开关。** 每一轮跑完，systemd 隔 1 秒再启动它。和上一版比，删掉了一个常驻程序、它的重启逻辑和一套单独的测试。
6. **把认领单独拆出来，带出了竞态，我们还是带上去了。** 审查指出了两处，我们修了一处，另一处判断不需要修，测试环境第 5 轮新用户实测就撞上了。从开票到修复合并 30 分钟。

## 走掉的人

我们刚开始记录新用户停在哪一步，几条记录就够看出该往哪查：有人在页面还显示「准备中」时离开了，其中一次环境其实已经好了，只是页面每 10 秒才查一次，还没来得及显示。

我们不知道一个人为什么停下。能改的，是页面让人等多久、等的时候让人看到什么。

## 动手之前，先一段一段量

我们拿到的第一个数字就是错的。我用 Claude Code 写 Orbi 的票、读它的改动，它告诉我准备环境「要 5 分钟左右」。我回它：5 分钟一个操作系统都装好了。然后我们从数据库里拉出时间戳，把等待拆成几段，每段归系统里不同的部分管：

| 环节 | 用时 | 由谁决定 |
|---|---|---|
| 请求等主机认领 | 3–41 秒，平均约 22 秒 | 主机上每分钟一次的定时器 |
| 开通沙箱 | 31–50 秒，平均约 37 秒 | 开通脚本 |
| 页面发现已就绪 | 0–10 秒 | 状态页每 10 秒查一次 |
| 读仓库、写出 3 条建议 | 94–198 秒 | 引擎和模型 |

前三行是动手前生产环境最近 8 次连接，最后一行是测试环境的 5 次运行。上面那次 79 秒的连接也落在这几个范围里：排队 32 秒，开通 37 秒，页面又过了 10 秒才显示。「5 分钟」大致是到看见第一个有用东西（建议）的时间，也就是常说的首次价值时间，不是准备环境的时间。两段不一样，修法也不一样。

那天夜里还定了一条口径：用户在操作的时间，比如挑仓库，不算等待。我们只压用户什么都做不了、只能干等的那几十秒。

## 瓶颈在排队，不在机器

开通脚本由一个每分钟触发一次的 systemd 定时器启动。它先做的事是给所有已有沙箱刷新凭据：GitHub 的安装令牌一小时就过期，所以每一轮都给每个沙箱换一个新的。刷完才去 Cloud 拿待开通的请求。生产主机上一轮要跑 1 分 28 秒到 1 分 41 秒，所以一轮紧接着一轮。新请求要是刚好在一轮开始后进来，几乎要把这一轮整个等完。记录里最坏的一次在旧版上，请求在队里排了 110 秒。

最直接的想法是改成 10 秒一次，我们差点就这么做了。读了脚本才发现这么改什么都不会变：一轮本来就接着一轮，每一轮照样先刷新全部沙箱，才去看新用户。问题在顺序，不在间隔。

## 从短轮询到长轮询：四版方案，一版比一版小

**第 0 版：定时器改成 10 秒。** 原因上面说了，没有上线。

**第 1 版：单独拆一个每 2 秒认领一次的任务。** 刷新照旧每分钟一轮，认领单独跑快的。能用，但本质还是轮询。我问了一句：为什么不做成基于消息的，这样就不用等了？

把请求从 Cloud 送到主机，列了三种做法：

| 做法 | 怎么做 | 结论 |
|---|---|---|
| A. 短轮询，问得更勤 | 就是第 1 版 | 简单；最多 2 秒延迟，不管有没有活都每 2 秒问一次 |
| B. 长轮询 | 主机发一个请求，Cloud 先不答，有活或到时间再返回 | 有新活约 1 秒内返回，主机仍然只往外连 |
| C. 推送 | Cloud 主动连主机 | 主机得开入站端口，我们的设计不允许，不采用 |

只能往外连的 worker，长轮询是常见的做法。GitHub Enterprise Server 3.12 的文档写着，自托管执行器[向 GitHub 发起一个 50 秒的长轮询](https://docs.github.com/en/enterprise-server@3.12/actions/hosting-your-own-runners/managing-self-hosted-runners/communicating-with-self-hosted-runners)，超时就再开一个，不需要任何入站连接；[Amazon SQS](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-short-and-long-polling.html) 取消息时最多可以等 20 秒。我们的主机和自托管执行器处境一样：能往外连，外面连不进来。

**第 2 版：长轮询加一个常驻程序。** Cloud 是跑在 Cloudflare Worker 上、用 D1 数据库的服务，新加了一个接口 `GET /api/internal/provisioning/wait`：请求最多挂 20 秒，每秒查一次库，有新请求就在下一次查询时返回。一次调用 20 次查询，在 D1 免费档每次调用 50 次的上限之内。它**只返回新请求**，失败后等重试的请求留在每分钟那条路上。不然一个刚失败的请求 1 秒后就会被重新认领，一次短暂故障就能把 3 次尝试机会用光。这一条是动手写代码前的独立审查查出来的。

主机这边，第 2 版要新写一个 Python 常驻程序：循环调用这个接口，认领请求，再通过新入口启动开通脚本。部署脚本要学会第一次启用它、代码一变就重启它，这个程序还要配一套自己的测试，接进持续集成。

**第 3 版：一个开关。** Orbi 已经按第 2 版开工了，我问能不能再薄一点。现有脚本里有三个事实可以利用：它没有全局锁，可以同时跑两份；刷新是一整段连续的代码，可以整段跳过；新接口返回的 JSON 和原来的待开通清单一模一样。于是 `provisioner.sh` 加了一个 `--claim-only` 开关：打开后跳过刷新，把 `/pending` 换成 `/wait`，认领、开通、回调全部复用原来的代码。每次运行只等一次、处理完就退出。

### 让 systemd 当循环

完整的服务文件就这些：

```ini
[Unit]
Description=Orbi Cloud provisioning fast claim (long-poll)
# 这个服务本来就是要不停重启的，关掉默认的启动限流
# （10 秒内启动 5 次就停掉），否则 Cloud 一出错它就被停了
StartLimitIntervalSec=0
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
EnvironmentFile=/etc/orbi-cloud/provisioner.env
ExecStart=/opt/orbi-cloud/host-provisioner/provisioner.sh --claim-only
Restart=always
RestartSec=1

[Install]
WantedBy=multi-user.target
```

`Restart=always` 让脚本正常退出后也会重启，每一轮跑完要的正是这个。每一轮都从磁盘重新启动脚本，部署时不用写任何重启逻辑，下一轮自然跑的就是新代码。这么做安全有两个前提。一是我们的部署先把新文件写成临时名，再改名替换，正在跑的那一轮读的还是旧文件；bash 是边执行边读脚本的，原地覆盖一个正在运行的脚本可能出错。二是这个服务装上时默认不启用。我们是在带 `/wait` 的 Worker 上线之后手动启用了一次，否则没有这个接口，它每秒都会撞一个 404。代价是每次重启记几行日志；接口正常、又没有新请求时，一分钟大约重启三次。

第 3 版比第 2 版删掉了什么：

| 第 2 版 | 第 3 版 |
|---|---|
| 新写一个 Python 常驻程序，自己循环 | 不写新程序，systemd 负责循环 |
| 程序认领后，再通过新入口调开通脚本 | 直接用开通脚本现有的认领和开通代码 |
| 部署脚本要会首次启用、代码变了重启 | 手动启用一次；之后每一轮都读最新部署的脚本 |
| 一套单独的 Python 测试，还要接进持续集成 | 在 4 个现有测试文件里加用例 |

空闲、接口正常的时候，长轮询的请求量大约只有第 1 版（每 2 秒问一次）的十分之一。

审查里还有两条细节进了第 3 版：认领失败时等 10 秒再退出，不空转打 Cloud；快路径跳过引擎缓存更新，因为遇上引擎发新版，那一步最长要 600 秒，会挡住下一次认领。

## 那个被提醒过的竞态

认领从每分钟那一轮里拆出来，就有两样东西同时在跑，审查找到了两处会撞车的地方。

第一处：「凭据被拒」回调不管请求处在什么状态都直接判失败，每分钟那一轮可能把快路径开通到一半的请求判死。这一条的修法写进了票里，是一个 SQL 条件：只有已经结束的请求才能被判失败。

第二处：每个租户只有一个模型密钥槽位，签一把新的，旧的就作废。认领时会签一把交给开通脚本，每分钟那一轮会给每个租户各签一把。如果那一轮恰好落在认领之后、开通脚本第一次调 Cloud 之前，脚本手里的密钥就作废了，以退出码 42 退出（日志写着 the key … was superseded），新用户第一次开通就看到「工作环境准备失败」。设计审查也点了这一处，给的修法是：刷新时跳过正在开通的租户。Claude Code 觉得认领现在只要 1 秒左右，没必要，就没写进票里。我也没拦。

那天晚上长轮询在测试环境上线，前 4 轮新用户实测都过了。第 5 轮在 22:50:15 被认领，4 秒后就这样失败了。自动重试在 22:51:38 开通成功。22:53 开了最高优先级的票，Orbi 在 23:23 合并了修复：刷新时跳过开通请求还在排队或进行中的租户，等它开通结束后的第一轮再把它加回来。

我从这件事记下的规矩：审查方指出的竞态，要么把修法写进票里，要么写一个测试证明它撞不上。「现在应该够快了」证明不了任何事。

## 剩下的等待去哪了

长轮询消掉了排队：之后测试环境上的每一轮，请求都在 1 到 2 秒内被认领。同一批的其他票压缩的是认领之后的活：

- 引擎从主机上常备的目录复制过去，不再从 GitHub 克隆；
- 沙箱用户一建好就开始拉用户的仓库，和后面的准备并行，并且以沙箱用户的身份拉，因为那是不可信的代码；
- 新沙箱跳过一个必然失败的 SSH 探测，直接走 HTTPS；
- 装好 Orbi 命令行就报告环境就绪，并立刻开始读仓库，不再等一个 30 秒一次的定时器；
- 页面上的进度每 2 秒原地更新，不再每 10 秒整页刷新。

加在一起，认领到环境就绪从约 25 秒降到了竞态修复后那三轮的 7、8 秒。下面是其中一轮，从点击到出建议：

## 等待的时候，页面上放什么

14 秒仍然超过了 Nielsen Norman Group 说的 [10 秒](https://www.nngroup.com/articles/response-times-3-important-limits/)注意力上限。所以页面上放的是真实进度，不是转圈：四个步骤（建好独立的工作环境、拉取你的代码、安装 Orbi、开始读你的仓库），每完成一步打一个勾，写上用了几秒。仓库的语言占比和最近一次提交从第 0 秒就显示，摘要大约第 25 秒出来。

展示过程是有研究依据的。哈佛商学院 Buell 和 Norton 2011 年的 [Labor Illusion](https://www.hbs.edu/faculty/Pages/item.aspx?num=40158) 论文（发表在 Management Science）里，受试者在两个结果完全相同的服务之间选。要等的那个如果把干活的过程展示出来，等 30 秒时有 62% 的人选它而不是立刻出结果的那个，等 60 秒时是 63%；如果只让人干等，30 秒时 42%，60 秒时只剩 23%。

同一篇论文里有一个更要紧的边界条件：过程展示得很卖力，结果却很差，人们给的评价最低。我们出过一个看起来就不对的结果：在中文页面上，仓库摘要是英文写的，因为写摘要和写建议的两段提示词都没说用什么语言。论文没测过这种情况，我们也没量过它的影响，但这条边界条件足够让我们先把它修掉。现在 Orbi 会把页面语言传给引擎。

## 结果

测试环境的新用户实测，时间是 10 月 11 日 23:28 到 12 日 02:20。每一轮都先把测试账号重置回未注册，再从「连接仓库」开始：

| | 改前 | 改后 |
|---|---|---|
| 连接（改前）或点击（改后）到页面离开「准备中」 | 79 秒（生产环境的一次连接） | 11.5–14.6 秒（4 轮） |
| 请求等待认领 | 生产 8 次连接 3–41 秒；最坏 110 秒 | 1–2 秒（5 轮） |
| 第一次出现仓库摘要 | 没有这一项 | 23–29 秒（5 轮） |
| 3 条建议 | 3 分 22 秒（测试环境基线） | 1 分 50 秒到 3 分 14 秒，中位数 2 分 01 秒（5 轮） |

第 5 轮用的是手机尺寸的窗口，中途被切到了后台，页面没有按时刷新；它的四个步骤在第 10.6 秒全部打勾，我们没把它算进第一行。3 分 14 秒那一轮，是模型那次写得比平时多一倍。这一段取决于模型输出多长，不在这次改动的范围里。5 轮里有 2 轮接着把一条建议交给 Orbi，两个合并请求都在约 9 分钟后合并。

这次改动 10 月 12 日 03:19 上了生产，生产跑的是同一份代码。改后这一列目前还是测试环境的数字。

## 活是谁干的

32 张票，31 张由合并的合并请求关闭，新增 9,001 行、删除 1,635 行。多数票在 01:00 前后一次开出，然后按依赖排队，所以开票到合并的中位数是 498 分钟；最快的是竞态那张修复，30 分钟。Claude Code 写票，并在合并前读每一个改动；这 31 张，由 Orbi 实现、另开会话评审、等持续集成通过后合并。

我做的是判断什么重要，问了两个问题：「为什么不基于消息？」和「能不能再薄一点？」。漏掉那个竞态，也是我的。

## 如果你的用户也在等

1. 用自己的时间戳把等待拆成几段，写清每段归哪个组件管。
2. 用户在操作的时间不算等待，只压他只能干看的时间。
3. 调间隔之前，先读一读你关心的那一步前面在跑什么。
4. worker 不能接入站连接，就用长轮询。快路径只发新活，重试留在慢路径上。
5. 让服务管理器当循环：`Restart=always`、`RestartSec=1`、`StartLimitIntervalSec=0`，部署时用改名替换文件。
6. 审查方点名的竞态，在有测试证明它撞不上之前，都当需求做。
7. 等待时展示真实进度；看起来不对的结果，先修好再往屏幕上放。

## 局限

改后的数字来自测试环境上几轮实测、一个很小的测试仓库，上线后我们还没在生产上量过。改前的数字混了生产和测试环境，每张表都写明了是哪个。写建议的时间仍然取决于模型写多少。
