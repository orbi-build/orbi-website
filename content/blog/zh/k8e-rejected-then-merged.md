[k8e](https://github.com/xiaods/k8e) 是一个内嵌 etcd 的 Kubernetes 发行版，497 星，维护者是 Deshi (Tommy) Xiao。9 月 20 日他开了 [#612](https://github.com/xiaods/k8e/issues/612)：给嵌入式 etcd 设计一套端到端健壮性测试，分四个阶段。第一阶段是故障后安全恢复，之后是多节点故障、备份可恢复和长期稳定性。

10:28（UTC+8）他给这张票打上 `ai-ready`。下面按公开的 PR、评审和票的标签历史，讲后来发生的事。

### 第一版被打回

11:37，Orbi 开了 [PR #613](https://github.com/xiaods/k8e/pull/613)，只做第一阶段：10 个新文件，2483 行。里面有操作历史记录器、恢复判定器（oracle），以及写入中途 SIGKILL 子进程、WAL 损坏、quota 等测试。

11:46，维护者贴出了代码质量工具（SonarCloud 和 DeepSource）标出的问题，Orbi 从 11:57 开始推修复。

13:21，维护者账号上的评审给出 **REQUEST_CHANGES**。这时 PR 是 2695 行，评审给了三条发现：

- **R1：判定器接受了一个不可能的状态。** 假设两个 CAS 都预期 revision 3，A 已确认成功，B 结果未知。如果恢复后读到的是 B 的值，这不可能发生，因为后执行的那个比较必然失败。判定器却接受了，因为它把结果未知的 CAS 当成了无条件写入。

  对应的操作历史：

  ```
  k is at rev 3
  A: CAS rev3 -> a  acked
  B: CAS rev3 -> b  unknown
  recovered: k = b
  oracle: OK   (should fail)
  ```

- **R2：被杀的进程同时在记账。** 记录器跑在测试要 SIGKILL 的那个进程里。一次写入可能已经被确认，但确认还没写进日志，进程就被杀了。这条写入会被降级成「未知」，就算它丢了，测试照样通过。票面要求的恰恰相反：记录器必须在被测节点之外。
- **R3：空值被当成不存在。** 空 payload 不做哈希，判定器就把「写入了空值」读成「键不存在」。空值键丢了，测试也能通过。

评审还指出，PR 正文里的 `Fixes #612` 会在只完成第一阶段时就关掉整张四阶段的票。

这几条都不是代码风格问题。每一条都意味着测试会在没恢复对的时候报「恢复正确」。对一套测试来说，这是最坏的失败：虚假的安全感。

### 同一个 PR 上，Orbi 自己的错

出问题的不只是代码。Orbi 的引擎在这个 PR 上报了三次自己的失败，每一次都写在 PR 评论里：

1. **12:28**，想加一个该仓库不存在的标签 `ai-awaiting-merge`。12:37 引擎放弃，把票标成 `ai-blocked`，意思是「下一步由人决定」。维护者 14:16 摘掉这个标签，14:41 又把 `ai-ready` 打回去，工作才继续。
2. **14:54**，Orbi 自己的独立评审输出里没有结论行，结果解析不出来。
3. **15:19**，续跑校验要求 PR 正文里必须有 `Fixes #612`，而这正是维护者评审要求删掉的那一行，而且删得有道理。

第三条 Orbi 始终没有自己消掉。更糟的是，这次校验失败没有只让这张票失败，而是让服务他仓库的整个 runner 进程崩溃。按 runner 自己的日志，15:19 到 22:10 之间崩了 84 次，他整个队列都停了（[orbi#1219](https://github.com/orbi-build/orbi/issues/1219)）。19:59 维护者在票下留言「继续修复吧」，之后也没有下文。这条规则对一次做完的票是对的，对分阶段的票是错的。引擎守着规则，对的是人工评审。

### 怎么修的

15:05，一个 commit（`f8e9dd9c`）改完了三条发现：

- 预期 revision 早于该键最后一次确认 revision 的未知 CAS，现在会被剔除。
- 子进程只托管 etcd 成员，客户端和记录器移到父进程，被杀之后记录器还活着。
- 每次 put 和 CAS 的 payload 都做哈希，空字符串也不例外。

R1 和 R3 补了正反两个方向的测试。PR 正文改成「Part of #612 — this PR lands the phase-1 layer only」。

22:12，第二轮评审给出 **APPROVED**。它逐条核对了修复，并提了两个合并前条件。一是独立跑一遍 race 测试。二是去掉 Orbi 第一个 commit message 里残留的 `Fixes #612`；评审认为只有 PR 正文会关票，所以把这一条标成可选。剩下的覆盖缺口设计文档里已经写明，评审也一一列了出来。38 秒后，22:13，维护者本人点了合并，记录里看不到这两个条件先被执行过。合并时的 CI：801 个测试，新增 49 个，0 失败。

### 票还是被关了

评审对 commit message 的判断错了。合并进默认分支的 commit message 里只要有关闭关键字，GitHub 就会关掉对应的票，不只看 PR 正文。合并后一秒，#612 被关成了 *completed*，关它的正是 Orbi 的第一个 commit。四个阶段只落地了第一个。第一轮评审警告的恰恰是这件事，结果它还是发生了，从唯一没修的那个地方漏了出去。

这是 Orbi 在这张票上的第四个错，也是后果最重的一个。我们引擎的规则要求 PR 正文里写 `Fixes #N`，交付 agent 又把它写进了自己的第一个 commit message。两轮评审都指出过这个关键字：第一轮说的是 PR 正文，第二轮说的是 commit。票还是关了。截至本文发布，#612 仍是关闭状态。

### 第二个 PR：从开出到合并 3 小时 12 分

第二天是 [#614](https://github.com/xiaods/k8e/issues/614)：rqlite 兼容性，M0 关口。维护者 15:21 给它打上标签。[PR #615](https://github.com/xiaods/k8e/pull/615) 改了 11 个文件，加了 3294 行。16:49 开出，从 17:33 起等待批准。维护者账号上先出现一条 LoopX 评审意见，20:00:52 他批准，29 秒后 Orbi 合并。

### 这件事说明什么

它不能说明 Orbi 一次就能做对。这次没有一次做对。维护者不得不出手：解除阻塞、把票放回队列，在 Orbi 停住时催它继续，最后绕过 Orbi 一条不适合他这张票的规则，自己合并。而一张四阶段的票，还是在第一阶段后就被关掉了。

它说明的是这样一个循环：评审可以说不，并给出理由，修复落在同一个 PR 上。在别人的代码库里接一张难票，从开 PR 到合并用了十个半小时。它也说明，每一个失败，包括 Orbi 自己的，都在公开记录里，任何人都可以拿这篇文章去对。Orbi 之后改了两处（[orbi#1219](https://github.com/orbi-build/orbi/issues/1219)）：PR 正文不合约，现在只让这一张票失败，不再拖垮 runner；Orbi 的工作流规范现在要求：分阶段的工作不能由一张票承载，维护者把每个阶段拆成子票，每个子票的 PR 只关闭它自己。
