On September 28 Orbi fixed three issues in forks of open-source projects: [pyinfra](https://github.com/orbi-build/pyinfra/pull/3), [chainloop](https://github.com/orbi-build/chainloop/pull/3) and [fedify](https://github.com/orbi-build/fedify/pull/3). All three PRs passed their test suites and Orbi's own independent review, and all three merged in the forks. Before sending any of them upstream, we checked them by hand, and two were wrong.

The chainloop one is a secret redactor. The issue was that a JWT sitting in front of an escaped quote got redacted together with the backslash. Orbi's fix trimmed trailing backslashes from each finding. It did fix the JWT. Run the merged code on two other inputs and you get this (placeholder shortened to `[REDACTED]` in the second):

```
input:  DB_PASSWORD=Zq8mLp2Vx9rT\n next
output: DB_PASSWORD=[REDACTED:generic-password]\n next

input:  password: s
        Host: services.example.com
output: pa[REDACTED][REDACTED]word: [REDACTED]
        Ho[REDACTED]t: [REDACTED]ervice[REDACTED].example.com
```

In the first, the detector reports the password as `Zq8mLp2Vx9rT\n`, with a literal backslash and `n`. The fix trims those two characters off the finding, so they stay in the output in clear text. In the second, the secret is one character long, and every `s` in the log gets replaced. Orbi's review comment on that PR reads, in full, `review: pass, no findings`.

The pyinfra fix had the same shape. The issue was CJK text misaligning a results table. The fix counted wide characters as two columns and aligned the issue's example, but it made 👍🏽 and a decomposed が worse than before. The review said `pass, no findings` there too.

The reviewer wasn't lazy. On both PRs it ran the tests and checked the issue's example. The example passed, because the example was never the problem. The regression was in inputs nobody thought to try.

### How we tested the harness

"We improved the prompt" isn't worth much without a number, so we built a benchmark that can fail.

For each of the three issues we took a private snapshot of the repository at the commit Orbi started from. The real Orbi runner ran the full loop on it: claim the issue, write the fix, open a PR, run the independent review, merge. Then a hidden grader that Orbi never saw scored the merged result.

Each grader was calibrated before use. It had to fail the original code, fail Orbi's merged fork PR (the one that shipped the regression), and pass a fix we had verified by hand. A grader that passes the bad fork PR measures nothing. For chainloop, the two failing checks are exactly the two outputs above.

Each variant changed one or two things from an earlier one (prompt, skill, toolchain, implementation model or review model), and variants ran in parallel overnight. There were 96 runs in total.

### What the harness changes were

Each rule came from reading a failed run's transcript, not from a list of best practices.

1. **Generate the inputs.** The first attempt just told the agent to compare behaviour before and after the fix. pyinfra went from 0/5 to 2/3, and the failures came from the agent choosing examples that were already fine: it tested U+0301, which was never broken, instead of U+3099. The next version required inputs to be generated by a program across whole character classes, with the counts written into `.orbi/regression.md`. After that, runs generated up to 2,756 inputs for the redactor and 1.19 million character units for the table.
2. **The oracle must not be the change.** One run with a strong model built its "expected" output from the rule it had just implemented, so it was comparing the fix with itself and got zero mismatches. The prompt now requires an oracle that doesn't depend on the patch: a reference library, the old behaviour, or an invariant.
3. **Cross-check reference implementations.** In the pyinfra environment, `wcwidth` 0.2.14 counts 👍🏽 as four columns. An agent that trusted it would have "proved" the regression was correct. `rich` gets it right. When several references exist, the agent now compares them and says which one it trusts and why.
4. **The characters you strip are data too.** The password leak only shows up when the secret itself ends in `\` or `\n`. Agents put backslashes after the secret, never inside it. The prompt now names this input class and asks which producers (here, detection rules) can emit such a value.
5. **Collision checks.** If a fix changes the text it searches for or replaces, test where else that text appears. This is the one-character `s`.
6. **Contribution rules come from the repository's tools.** Our own harness text had an example saying "add a changelog fragment, don't edit the generated changelog". fedify uses `sacho` with materialization on, so every upstream commit edits both files, and that example steered Orbi wrong. The rule now says to run the repository's own checker (`sacho check` here) and to put that tool on the runner's `PATH`.

With the same cheap model, the original harness passed 6 of 15 runs. v13 to v15 passed 28 of 30: pyinfra 11/11, chainloop 10/12, fedify 7/7. The two repositories fail differently under the original harness: pyinfra's regression came back in all five runs, while the chainloop leak showed up in one run out of six. A rare regression like that is the kind a reviewer waves through.

### What the numbers don't say

A better model didn't rescue the original prompt in this data, but there is only one run each for luna + sol (v2) and Opus 5.5 (v7) on pyinfra, and v7 used the v1 prompt, not the original. That's too few runs to claim that models don't matter, and chainloop shows they do. The two chainloop failures in v13–v15 were cheap-model reviews that misjudged whether `\n` was data or an escape. With `gpt-5.6-sol` as reviewer and `deepseek-flash` still writing the code, chainloop went 4/4, and strong-model reviews on chainloop total 7/7. For security-sensitive code, the cheap model writes the fix and a stronger model reviews it.

We also tuned the prompt on the same three issues we measured it on. There's no held-out set yet, so 28/30 is a training score. The next step is to run v15 on issues it has never seen, each with a grader calibrated the same way.

fedify also turned out different from what we first assumed. Orbi's original code there was compliant. What went wrong was process: a first-time contributor has to claim the issue first, and bug fixes go to a maintenance branch. The grader now runs `sacho check`, and the contribution skill tells the agent to read `CONTRIBUTING.md` and any AI policy before it writes anything.

The upstream pyinfra PR, still open, was rewritten by hand with Claude Code after these regressions were found; the chainloop and fedify ones haven't been sent yet. Orbi's fork PRs are still public, with the flaws described above.

### Where it lives

The prompt changes, two standalone skills (`orbi-regression-guard` and `orbi-upstream-contribution`) and the whole benchmark (instance setup, hidden graders, scoring scripts) are on the [`harness/regression-guard`](https://github.com/orbi-build/orbi/tree/harness/regression-guard) branch of Orbi. They aren't the default yet. They make each delivery slower and use more tokens, because generating inputs and running reference implementations isn't free.

Better review isn't the main lesson here. What changed the numbers was forcing the agent to test inputs it didn't pick, against an answer it didn't write. The model mattered at the edges, but the harness decided what got checked.

If you run coding agents unattended, try one thing this week: take a merged agent PR, write the input you think it gets wrong, and see whether your reviewer would have caught it. [Orbi Cloud](https://orbi.build/cloud/?ref=blog-harness) runs this loop on your own issues.
