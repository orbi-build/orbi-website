Orbi is two things wrapped around each other. One is the harness: the prompts, skills, tools on the runner's `PATH`, and the loop that has one agent write a fix and another review it. The other is the models inside it. When a delivery goes wrong, you can't tell from one run which half failed. So we crossed harness versions with models and ran the whole loop 96 times on the same three issues, to find the combination Orbi should ship with.

### Why now

On September 28 Orbi fixed three issues in forks of open-source projects: [pyinfra](https://github.com/orbi-build/pyinfra/pull/3), [chainloop](https://github.com/orbi-build/chainloop/pull/3) and [fedify](https://github.com/orbi-build/fedify/pull/3). All three passed their tests and Orbi's own review. Before sending any upstream we checked them by hand, and two were wrong.

The chainloop fix, in a secret redactor, leaks part of a password:

```
input:  DB_PASSWORD=Zq8mLp2Vx9rT\n next
output: DB_PASSWORD=[REDACTED:generic-password]\n next
```

The detector reports the password as `Zq8mLp2Vx9rT\n`, ending in a literal backslash and `n`. The fix trims those two characters off the finding, so they stay in the log. A one-character secret, `s`, made it replace every `s` in the text. The pyinfra fix aligned the issue's CJK example and made 👍🏽 and a decomposed が worse. On both PRs, Orbi's review comment reads `review: pass, no findings`.

That review ran the tests and checked the issue's example. The example passed. The regressions were in inputs nobody tried.

### The benchmark

For each issue we took a private snapshot of the repository at the commit Orbi started from. The real Orbi runner ran the full loop on it: claim the issue, write the fix, open a PR, review, merge. A hidden grader that Orbi never saw then scored the merged code, together with the repository's own checks and full test suite.

Each grader was calibrated first. It had to fail the original code, fail Orbi's merged fork PR, and pass a fix we had verified by hand. For chainloop, the grader's two failing checks on the fork PR are the password tail and the one-character secret.

Variants changed the prompt, the skills, the tools on `PATH`, the implementation model, the review model, or a mix. The models were `deepseek-flash`, `gpt-5.6-luna` and `gpt-5.6-sol` through Pi, Opus 5.5 through a Claude Code bridge, and GLM 5.3 flash through a zcode bridge. In the two bridge columns the same model both implements and reviews, and the agent loop is the bridge's, not Pi's.

### The grid

Rows are harness versions, each built on the one above unless noted. Columns are model setups, written as implementer / reviewer. Cells are passes / runs across the three repositories.

```

v0  original harness           6/15    1/3
v1  compare before/after       5/7                        1/3
v4  v1 as a separate skill     1/3
v5  generated inputs + oracle  4/4               1/2      2/3
v10 v5 + contribution skill    1/2
v11 independent oracle, tools  6/9                        3/4
v13 + stripped chars as data   11/12
v14 + reference cross-check    8/9                                2/3
v15 + collision checks         9/9                                        4/4*

ds = deepseek-flash   * chainloop only
```

The grid is sparse. We filled the cells that answered the question in front of us at the time, not a full factorial. Most non-deepseek cells have two to four runs.

### What the harness changes did

Holding the model at `deepseek-flash`, the harness went from 6/15 to 28/30 across v13–v15. Each rule came from reading a failed run's transcript:

1. **Generate the inputs.** v1 asked the agent to compare before and after, and it picked examples that were already fine. It tested U+0301, never broken, instead of U+3099. From v5 on, inputs are generated by a program across whole character classes, and runs produced up to 2,756 inputs for the redactor and 1.19 million character units for the table.
2. **The oracle must not be the change.** A `sol` run computed its "expected" output from the rule it had just implemented and found zero mismatches. v11 requires an oracle that doesn't depend on the patch.
3. **The characters you strip are data.** The password leak needs a secret that itself ends in `\` or `\n`. Agents only ever put backslashes after the secret. v13 names that input class.
4. **Cross-check references.** `wcwidth` 0.2.14 counts 👍🏽 as four columns; `rich` counts two. An agent that trusted `wcwidth` would have "proved" the regression correct. v14 makes the agent compare references and say which it trusts.
5. **Collision checks.** If a fix changes the text it searches for or replaces, test where else that text appears. That's the one-character `s`, in v15.
6. **Contribution rules come from the repository's tools.** An example in our own prompt said not to edit the generated changelog. fedify's `sacho` setup edits it on every commit, so our example steered Orbi wrong. From v11, the agent runs the repository's own checker (`sacho check`), and the tool is on the runner's `PATH`.

The v1 rule packaged as a separate skill (v4) scored 1/3 against 5/7 as prompt text. The transcripts show the skill was read, and three runs are too few to say the packaging matters. Either way the rule still let the agent pick its own samples, which was the real problem.

### What the models did

Model swaps are harder to read, because each one came with a different prompt version and, for Opus and GLM, a different agent loop.

- On the original harness, `luna` implementing and `sol` reviewing scored 1/3, and it missed the same pyinfra regression as `deepseek-flash`.
- Opus 5.5 built the deepest probes of any model, 1.19 million character units in v12, but on v11's prompt it still passed 3/4 against deepseek's 6/9 on the same prompt. That's too few runs to call either better.
- GLM 5.3 flash on v14 passed pyinfra and chainloop. It failed fedify because its bridge ignores skills, so the contribution rules never reached it. That's an integration gap, not a model result.
- The one clean reviewer swap is v15 with `sol` reviewing instead of `deepseek-flash`, on chainloop only: 4/4 against 4/4. In v13 and v14 the two chainloop failures were deepseek reviews that misjudged whether `\n` was data or an escape, which is why we tried it, but this data doesn't separate the two reviewers yet.

The harness moved the numbers far more than any model swap we ran. That's a statement about these 96 runs, not a claim that models don't matter.

### Where we are

The leading candidate is v15 with `deepseek-flash` implementing and reviewing: 9/9 across all three repositories. v13 is close at 11/12, and v5 passed all four of its runs, too few to lean on. `sol` as reviewer is the next thing to test on all three.

There are three limits, and they are real. We tuned the harness on the same three issues we scored it on, so there's no held-out set yet, and 9/9 is a training score. The grid is sparse. And the graders only catch defects we knew to look for. The next round is v15 against issues it has never seen, each with a grader calibrated the same way.

The upstream pyinfra PR, still open, was rewritten by hand with Claude Code after these regressions were found. The chainloop and fedify ones haven't been sent yet.

### Where it lives

The prompt changes, two standalone skills (`orbi-regression-guard` and `orbi-upstream-contribution`) and the benchmark itself are on the [`harness/regression-guard`](https://github.com/orbi-build/orbi/tree/harness/regression-guard) branch of Orbi, under `bench/oss-upstream/`: instance setup, hidden graders, scoring and aggregation. They aren't the default yet. Generating inputs and running reference implementations makes each delivery slower and costs more tokens.

If you run a coding agent, try one thing this week: take a merged agent PR, write the input you think it gets wrong, and see whether your reviewer would have caught it. [Orbi Cloud](https://orbi.build/cloud/?ref=blog-harness) runs this loop on your own issues.
