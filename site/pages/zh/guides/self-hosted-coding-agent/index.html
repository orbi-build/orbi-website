开源 AI 编程 agent，从 Issue 做到发版

Orbi 是面向 GitHub 仓库的开源 AI 编程 agent。把运行程序装在自己的机器上、接入模型，在 Issue 里写清要改什么。Orbi 实现改动，另开会话独立评审，通过合并检查后合并。需要发版时，再用单独的发版票按仓库流程发布。

安装前先判断

开源 AI 编程 agent 怎么选

Orbi 从 GitHub Issue 接需求，把改动做到独立评审和合并。安装前，先确认这种交付方式适不适合你的仓库。

把需求和验收标准写进 Issue。
说清要得到什么结果，以及怎样检查。终端或 IDE 里的交互工具照常处理你想逐步确认的改动，Orbi 则按 Issue 交付任务。

确认合并和发版由谁决定。
Orbi 的常规交付会在独立评审和检查通过后合并。想由人逐次决定合并，就要把这个要求列入选型条件。功能票与发版票分开，发版另开一张带 ai-ready 和 ai-release 标签的 Issue。

自己维护运行程序、模型和 GitHub 授权。
自托管时，这些配置由你管理。如果接的是托管模型，代码上下文仍可能发给模型服务。用本地模型改变的是推理位置，Issue 和 PR 仍在 GitHub 上。具体接法见 provider 文档。希望把运行维护交出去，可以看下面的自托管与 Cloud 对比。

想比较更多工具，可以先读 OpenCode 替代方案和 Orbi 与 OpenHands 对比。也要核对具体跑法：OpenCode 也能跑在 GitHub Actions 里，有终端界面不等于只能在终端使用。

第一次先交一张结果能核对的小票，看看 PR 和评审证据，再把更多需求放进任务池。

跑在你的代码旁边

在自己机器上跑起来要什么

三样东西：Python runner、一个它能连上的模型、GitHub 访问。下面的命令照抄自入门指南。先按指南选好仓库、建立 orbi.toml、配置模型，再在 Orbi 的检出目录里运行后面的示例。下面的服务命令适用于 Linux；macOS 按入门指南操作。

curl -LsSf https://raw.githubusercontent.com/orbi-build/orbi/main/install.sh | bash

需要 Python 3.14、uv、git、gh 和 systemd 用户会话（macOS 是 launchd）。Node ≥ 22.19 是安装脚本唯一不替你装的依赖。

  1. 01 · 安装
    装上 runner

    脚本用 uv 装 Python 3.14 和 Pi CLI。orbi setup 只负责检查这些前置，不会替你装系统包或 gh。

  2. 02 · 模型
    接一个模型

    任何 OpenAI 兼容 API 都行：把模板复制成 .orbi/pi-providers.json，在 orbi.toml 里选 provider（DeepSeek 有现成模板）。ChatGPT/Codex 订阅也可以：在交互式 pi 会话里跑 /login codex。

  3. 03 · GitHub
    给它 GitHub 访问

    GitHub CLI 2.94 以上并已登录。Issue、标签、PR 和合并都走它；gh auth status 告诉你现在的状态。

  4. 04 · 首次交付
    跑一个 tick，看它合并

    给一张 Issue 打 ai-ready。一个 tick 只做一件事：恢复一个开着的 PR，或认领一张 Issue（先 p0，再 bug，再 feature）。timer 每五分钟做同样的事。

mkdir -p .orbi
printf '%s\n' 'DEEPSEEK_API_KEY=replace-me' > .orbi/env
chmod 600 .orbi/env

key 不写进 provider JSON。它放在 env 文件里，由 systemd unit 在服务启动时加载。 在当前终端手动检查前，也要导出 provider 的 key；或者使用已在 Pi 中登录的模型。

pi --print "reply with the single word: ok"
PYTHONPATH=src python3 -m orbi.runner --config orbi.toml
systemctl --user list-timers 'orbi@*.timer'

第一条命令只检查 Pi 自己选中的模型，不读取 orbi.toml 中的 provider 配置；这条配置路径要先按 provider 文档核对，再运行 tick。一个 tick 最多认领一张 Issue。最后一条命令能看到 timer 的下一次触发时间。

两种跑法

自托管还是用 Cloud

同一条交付产线。区别在于机器归谁跑，模型费用归谁付。

自托管Orbi Cloud
跑在哪你自己的机器，systemd 用户 timer（macOS 是 launchd）。Orbi 的基础设施。用 GitHub 登录，接入仓库就能用。
你要配置什么安装脚本、orbi setup、一个模型 provider。什么都不用装。每个接入的仓库在独立的 Unix 用户下运行。
模型你自己的：任意 OpenAI 兼容 API，或 Codex 订阅登录。套餐内包含。
花多少钱Orbi 按 AGPL-3.0 免费使用，模型费用付给你的 provider：169 次合并交付实测，非高峰中位 $0.082（按 DeepSeek 牌价）。先在你自己的仓库上试 __FREE_DELIVERIES__ 次合并交付，不用绑定信用卡。Solo：US$__SOLO_MONTHLY_USD__/月，__SOLO_INCLUDED_TOKENS__ token。Pro：US$__CLOUD_MONTHLY_USD__/月，__INCLUDED_TOKENS__ token。
额度用完时自托管没有 Orbi 侧额度，provider 按用量继续计费。只暂停新交付，不超额计费。

常见问题

装它之前问得最多的几句

数据放在哪里？
运行状态保存在你自己的机器上。配置在 orbi.toml，key 在 gitignore 掉的 .orbi/ 状态目录，任务 worktree 在 .worktrees/ 下，日志在你用户的 journal 里。GitHub 保存 Issue、PR 和 Release。使用托管模型时，任务中发送的代码上下文也会交给模型提供商。

能用本地模型吗？
可以。provider 文档自带 Local Qwen 模板（local-qwen.json，Qwen3.8-27B），任何 OpenAI 兼容端点都走同一个位置。

这是 Claude Code 的自托管环境吗？
不是。Anthropic 的 Claude Code 自托管环境（Team/Enterprise 公测）把 Claude Code 云会话的执行搬到你自己的机器，但控制面仍在 Anthropic、会话内容仍发往 api.anthropic.com、只支持 GitHub 仓库。Orbi 是另一回事：你自己的 runner、你自己的模型，跑一条 Issue 到发版的线，没有 Anthropic 控制面、不分套餐——给 Issue 打上 ai-ready，它就合并一个经过评审的 PR。

怎么暂停新任务？
停 timer：systemctl --user disable --now orbi@1.timer，每个启用的 timer 各停一次。这会暂停后续定时启动，已经开始的任务会继续。修改文件前，还要检查有没有正在运行的 service。什么都不删，重新启用就能恢复。彻底卸载的步骤在运维文档里。

一张 Issue 换来什么？
一个带证据的 PR、一次能直接修复分支的独立评审，以及只合并审过的那个 head。发版是另一张票：打上 ai-ready 和 ai-release 标签，Orbi 打 tag、发布 GitHub Release。整条产线见Issue 到发版。

和 Devin 比怎么样？
配置、价格和交付产线，逐项对比见 Orbi vs Devin。

runner 在 agent 外面做了什么？
Pi 只知道自己那个会话。挑 issue、让评审单独成一个会话、决定什么能合并，都是 runner 的事，详见 Orbi 怎么搭在 Pi coding agent 上。

自己的机器，自己的发版

机器是你的，发版也是你的

给下一张 Issue 打上 ai-ready，看着它合并。想发版时，开一张发版票打上 ai-ready 和 ai-release，Orbi 打 tag 发版。
