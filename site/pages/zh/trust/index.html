六项保护

你的代码如何受到保护

每一项保护都链接到它的文档，以及证明它的测试（如果有）。

  • AI 打不开的门禁

    改动只有在满足全部条件时才会合并：审查结论绑定在确切的 commit 上；仓库有 CI 时，该 commit 上的 CI 必须通过；head 没有变；base 是最新的。合并锁定在被审查的那个 commit 上。
  • 审查者不是写代码的那个

    审查在一个独立会话里进行，它看不到作者的思路，还可以换成另一家供应商的另一个模型。AI 永远不会自己批改自己的作业。
  • 最终控制权留在 GitHub

    分支保护由 GitHub 执行，不由 Orbi 执行。Cloud 只能访问你选择的仓库；卸载 GitHub App，访问立即终止，不需要经过我们。
  • 记录就在你的仓库里

    每一步都写在你看得见的地方：你自己仓库里的 Issue、PR 和评论，而不是一个需要你信任的仪表盘。一个 run_id 把一次运行的评论、PR 和日志串在一起。
  • 宁可停下，也不瞎猜

    出错立即失败。审查与修复最多五轮。做不完的交付会被标记为 ai-blocked 并写明原因，等人来决定。
  • 开源，没有任何锁定

    引擎以 AGPL-3.0 开源，在你自己的仓库上永久免费运行。任何 OpenAI 兼容模型都能用。明天停用，也没有任何东西需要导出。

你的代码去了哪里

自托管还是 Cloud，说清楚

  • 自托管
    在你自己的机器上

    你的仓库、GitHub token 和模型 key 都留在运行 Orbi 的机器上，不会上传给我们。代码只会发给你配置的模型端点；用本地模型，代码就完全不出你的环境。

    引擎安全模型

  • Cloud
    在我们运营的机器上，只在交付期间

    托管 worker 只克隆你授权的仓库。每个客户以独立的操作系统用户运行，与其他客户隔离，接触不到你的生产凭据或其他仓库。交付结束后静默 120 分钟，工作副本即被删除。

    模型：Cloud 默认使用平台模型通道，运行的是 DeepSeek，因此这个通道上你的代码和提示会发送给 DeepSeek。如果这不适合你的代码，可以填入自己的模型 key；它加密存储，只会以掩码形式显示。

不在保障范围内

我们不承诺的事

保障只有写清楚边界才有价值。下面是我们的边界，持续维护的完整清单在安全矩阵里。

01没有分支保护，Orbi 里没有任何东西能阻止 agent 推送你的主分支

Agent 被要求永远不推送、不合并 base 分支，但指令不等于强制。真正执行的是 GitHub 的分支保护或 ruleset。在 Orbi 合并任何东西之前，请先开启它，并要求状态检查通过。

02没有 CI，就没有测试证据

没有上报任何检查的 PR，在独立审查和其他门禁通过后仍然可以合并，只是它的测试不会被报告为通过。Orbi 门禁的强度取决于你提供的 CI。

03要求批准评审，会让每次交付都停下

Orbi 以同一个 GitHub 身份开 PR 和合并 PR，而 GitHub 不允许作者批准自己的 PR。如果 base 分支要求批准，Orbi 会等一个人逐个批准。这是一个合理的选择，这里说明了怎么做。

04发版走自己的门禁，不经过 PR 审查

发版任务可以先把版本提交直接推送到 base 分支，再打 tag、发布说明。

05测试通过，不等于做的是你想要的

测试证明代码符合测试，不证明测试符合你的本意。请在 Issue 里写清验收标准；如果希望每次合并前由人确认业务意图或界面文案，可以打开人工验收门。
