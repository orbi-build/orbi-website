九个问题

让 AI 合并代码之前，团队最常问的问题

开发者调查里反复出现的顾虑是：AI 写的代码是否安全、隐私、控制权、锁定、费用和可追责。下面是 Orbi 对每一项的回答。

  • 01 · 安全
    AI 写的代码会搞坏主分支，或者引入漏洞吗？

    改动只有在满足全部条件时才会合并：独立审查会话给出通过结论，并绑定在确切的 commit 上；仓库有 CI 时，该 commit 上的 CI 必须通过；head 没有变；base 是最新的。合并锁定在被审查的那个 commit 上。审查者把安全问题定为 Blocker 级；你的 CI 检查的任何东西，比如代码扫描或密钥扫描，都会成为合并门禁。Orbi 本身不带安全扫描器，所以请把你信任的扫描工具放进 CI。

    安全矩阵：每道门禁及证明它的测试

  • 02 · 审查
    代码会由写它的 AI 以外的东西来检查吗？

    一定会。审查在一个独立会话里进行，它看不到作者的思路，还可以换成另一家厂商的模型。而且它真的会说"不"：在 PR #1023 里，它打回了第一版，指出了具体的文件、行号和修法。

    PR #1023 · 更多公开交付

  • 03 · 隐私
    谁能看到我的代码？

    自托管：你的仓库、GitHub token 和模型 key 都留在你的机器上，不会上传给我们。代码只会发给你配置的模型端点；用本地模型，代码就完全不出你的环境。

    Cloud：托管 worker 只克隆你授权的仓库，每个客户以独立的操作系统用户运行，交付结束后静默 120 分钟即删除工作副本。Cloud 默认的模型通道运行的是 DeepSeek，它会收到交付所需的提示和仓库上下文；填入自己的模型 key，就改为发给你选择的供应商。只有在需要执行服务条款时，我们才可能查看 Issue 文本和仓库内容。

    Cloud 安全 · 隐私政策

  • 04 · 控制权
    我能一直掌握控制权吗？

    分支保护由 GitHub 执行，不由 Orbi 执行。Cloud 只能访问你在 GitHub App 安装里授权的仓库，没有任何组织或账户级权限；卸载 App，访问立即终止，不需要经过我们。你可以在 Issue 下留言纠正正在进行的交付，关闭 Issue 来停止它，用 ai-blocked 标签拦住合并，或者打开人工验收门，让每次合并前都有人签字。

    每项权限的用途 · 如何停止交付

  • 05 · 锁定
    我会被 Orbi 或某一家 AI 厂商锁定吗？

    不会。引擎开源，记录在你的仓库里，Pi 支持的任何模型都能用来写代码和审代码。详见上面的每一层都不锁定你。

  • 06 · 费用
    账单会吓我一跳吗？

    Cloud 套餐包含每月的模型额度，不按 token 收超额费用。额度用完后，新交付会暂停；如果你填了自己的 key，就改用你的 key 继续；已经在跑的工作照常完成。试用不需要绑卡。自托管免费，模型费用直接付给模型供应商。

    限制与额度 · 价格

  • 07 · 失败
    它做不到的时候会怎样？

    它会停下来告诉你。出错立即失败，没有静默兜底；审查与修复最多五轮；做不完的交付会被标记为 ai-blocked 并写明原因，交给人决定。它从不强制推送共享分支。

    工作流

  • 08 · 追溯
    我能查清楚到底发生了什么吗？

    每一步都写在你看得见的地方：你自己仓库里的 Issue、PR 和评论，而不是一个需要你信任的仪表盘。一个 run_id 把一次运行的评论、PR 和日志串在一起。Orbi 自己就是这样公开构建的。

    公开证据 · 所有已合并的 PR

  • 09 · 合规
    你们有 SOC 2 或 ISO 27001 认证吗？

    目前没有，我们也不会暗示有。Cloud 依赖 GitHub、Vultr（托管 worker）、Cloudflare、Stripe 和你的模型供应商，隐私政策里都列明了。如果你的制度要求供应商必须有认证，可以把开源引擎部署在你已经批准过的基础设施上。

不在保障范围内

我们不承诺的事

保障只有写清楚边界才有价值。下面是我们的边界，持续维护的完整清单在安全矩阵里。

01没有分支保护，Orbi 里没有任何东西能阻止 agent 推送你的主分支

Agent 被要求永远不推送、不合并 base 分支，但指令不等于强制。真正执行的是 GitHub 的分支保护或 ruleset。在 Orbi 合并任何东西之前，请先开启它，并要求状态检查通过。

02没有 CI，就没有测试证据

没有上报任何检查的 PR，在独立审查和其他门禁通过后仍然可以合并，只是它的测试不会被报告为通过。Orbi 门禁的强度取决于你提供的 CI。

03要求批准评审，会让每次交付都停下

Orbi 以同一个 GitHub 身份开 PR 和合并 PR，而 GitHub 不允许作者批准自己的 PR。如果 base 分支要求批准，Orbi 会等一个人逐个批准。这是一个合理的选择，这里说明了怎么做。

04发版走自己的门禁，不经过 PR 审查

发版任务可以先把版本提交直接推送到 base 分支，再打 tag、发布说明。

05测试通过，不等于做的是你想要的

测试证明代码符合测试，不证明测试符合你的本意。请在 Issue 里写清验收标准；如果希望每次合并前由人确认业务意图或界面文案，可以打开人工验收门。

06Cloud 按现状提供，不保证结果正确

服务条款不保证服务不中断、不保证使用某个特定的模型供应商、不保证交付成功或改动正确；你合并和部署的东西仍由你负责。上面的门禁是 Orbi 赢得信任的方式，条款则把承诺和不承诺的内容写清楚。
