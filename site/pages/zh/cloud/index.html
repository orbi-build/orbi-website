ORBI CLOUD 是什么

托管 Runner，GitHub 仍是唯一事实源

Orbi Cloud 跑的是与自托管 Orbi 相同的 GitHub 原生产线——Issue 进，Worktree、测试、独立审查与修复、精确合并——只是运行在由我们维护的基础设施上。你的工作流一点不变：Issue、PR 和发布证据都留在你自己的仓库里。

  • 交付闭环
    GitHub Issue 进，打好 Tag 的 Release 出

    能改代码、会重跑测试的独立审查，exact-head merge（只合并审过的那个 Head），再到冻结 SHA、打 Tag、发布 GitHub Release、关闭 milestone——你的仓库本来就懂这条闭环，不需要引入第二个工作区。

  • 模型
    模型用量包含在内，成本摊在明面上

    计划内含每月 20 亿 token；超出部分按公开的 $0.10/100 万 token 计费。我们不在你的 token 上赚差价——单次交付的实测成本就写在下面。

  • 运营
    恢复、合并门禁、独立审查

    交付产线的运营层，由我们承担。

  • 发版
    发版由你发起，Orbi 来执行

    发版从不是全自动。你开一张 release 票并打上 ai-release 标签——这个标签只有人能打。发版的测试验收就是你仓库的 CI 结果——release commit 上的 GitHub Actions check run——所以 CI 里放什么，决定了 Orbi 替你保证什么：放单测，它保证代码逻辑；放业务流程的 e2e，它保证业务闭环。不放 CI 也是一种选择：没有任何 check run 时，两道门禁都放行，release 照样能发——只是失去了唯一的测试验收闸门。之后 Orbi 冻结 SHA、打 Tag、发布 GitHub Release、关闭 milestone。

成本，实测

我们不在你的 token 上赚差价

实测于 2026-09-10，样本为我们自己仓库的 n=46 次真实交付（Python、完整 CI、Issue 写得规范）：单次交付中位 2,220,637 tokens，均值 4,667,630——按 DeepSeek V4.1 Flash 官方牌价约 $0.04–0.11 一次。token 构成：92.7% cacheRead、3.4% input、0.7% output。按实测均值，计划内的 20 亿 token 约够 430 次交付/月。

  • 只测了我们自己的仓库
    这是我们仓库的实测区间——不是对所有人的承诺

    Python、完整 CI、Issue 写得规范，让我们的 context 偏短。context 更长、测试更慢、Issue 更模糊的仓库会落在分布的其他位置。这些数字只说明一件事：我们仓库的实测区间。

  • 缓存是承重墙
    92.7% cacheRead 依赖 provider 支持 prompt caching

    整套成本结构建立在缓存命中上。换到不支持 prompt caching 的端点——每个 token 都按 miss 计价——同样的工作成本大约要涨一个数量级。

  • 按 totalTokens 计
    数字是 totalTokens，含 cacheRead

    这是 provider 实际计费的口径。只算 input + output 会藏掉大部分真实消耗，把数字做好看——和这一段的目的正好相反。
