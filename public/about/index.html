Why Orbi exists

A lights-out factory for software

  • One person, several businesses. I run Muyan, supa.is and Orbi on my own, so I needed agents that own development end to end.
  • Built for models that keep getting better. Orbi doesn’t hard-code today’s model limits into the line. The acceptance criteria and merge gates stay put, the model at each station can be swapped for a stronger one, and every step forward leaves fewer decisions for a person.
  • Software goes lights-out. Manufacturing already has lights-out factories, once the acceptance standard is set. Software can work the same way when each Issue says what done looks like.

How Orbi works

Where AI does the work, and where a person decides

AI agents do

  1. Turn your one-sentence request into an Issue with acceptance criteria, then write a plan
  2. Write the code and the tests on a branch
  3. Review it with a second, independent agent and fix what the review finds
  4. Merge once your CI passes on the latest base
  5. Tag the release and record every step on the Issue; ops Issues (deploy, merge a given PR, investigate) post the real commands and output

You decide

  • What gets built: you say what you want, or approve the Issue Orbi wrote
  • What happens when Orbi stops and asks a question
  • The final controls: branch protection, required checks and access all stay on GitHub
  • Which model runs: any model Pi supports, hosted or local

How I write this site

Every claim points to its source

  1. Numbers link to where they came from: a GitHub record, a document or the query I ran.
  2. Pages show their dates. Each post shows when it was published, and an updated date when it has been revised. I change a date only when the content changes.
  3. Tests say what they ran on: the version, the model and the date.
  4. Other products are described from their current official docs, checked when the page is written.
  5. Found a mistake? Tell me in the Telegram group or open an Issue on orbi-build/orbi-website. I fix it and update the page’s date.
