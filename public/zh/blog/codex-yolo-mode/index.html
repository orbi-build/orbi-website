Codex YOLO mode 会放开什么权限

Lawrence Liu · 2026-10-16

Codex YOLO mode 会跳过审批和本地沙箱。本文用 Linux 实测它放开了哪些操作，并说明 Codex auto mode 是什么、旧 full-auto 命令怎样迁移。

Codex YOLO mode 指的是 --yolo，它是 --dangerously-bypass-approvals-and-sandbox 的别名。开启后，Codex 不再询问审批，也不再使用自身的本地沙箱。运行它的环境必须另有隔离，例如一次性虚拟机或限制过权限的 CI runner。只想让 agent 自动修改仓库、保留沙箱，可以先用 codex -a never exec --sandbox workspace-write "<任务>"。Codex auto mode 是另一个预设，遇到审批仍会停下来等人，下文有详细说明。

我是 Lawrence Liu，Orbi 的创始人。2026 年 10 月 16 日，我在 Linux 上用 Codex CLI 0.159.3 实测了这几种配置。Orbi 运行的是编码 agent Pi，Codex 接入走 Pi 的 openai-codex provider，不运行 Codex CLI；本文命令供直接使用 CLI 的开发者参考。

怎样启动 Codex YOLO mode

在已经做好外层隔离的一次性运行环境中执行：

codex exec --yolo "Run the tests and fix the failures."

完整参数的含义相同：

codex exec --dangerously-bypass-approvals-and-sandbox \
  "Run the tests and fix the failures."

OpenAI 的 CLI 文档 定义了这两个写法，并要求运行环境有外部防护。新建一个 Git worktree 不提供操作系统层面的隔离：agent 仍以你的系统用户身份运行。

虚拟机或容器内部可读的文件和凭据，进程依然能够访问。本次实验的外层环境隐藏了真实 home 目录和其他进程，只暴露假的可写测试目录，没有 GPU 设备。模型请求和本地测试服务仍需要网络。

实测 Codex YOLO mode 能执行什么

我让 agent 在三种配置下各运行一次相同的 Python 探针：向仓库内写文件、向仓库外同级目录写一个无害文件，再请求本机 loopback HTTP 服务。同级目录放在 home 下的 cache 中，避开工作区和系统临时目录。用 /tmp 做越界目标容易测错，因为工作区权限可能包含临时目录。

每次配置都用新的外层沙箱，挂载和网络规则相同。--ignore-user-config 与独立 CLI home 排除日常配置的影响。登录认证临时复制进去，运行后删除；组织管理的要求仍可能限制实际权限。

三次 CLI 运行都实际执行了探针。写入被拦截时返回只读文件系统错误，网络被拦截时返回 “Operation not permitted”。我还通过 Codex 内置的 :read-only、:workspace 权限配置直接运行了探针，边界结果相同。

这组实验只记录当前 Linux 环境里的三项操作，没有测试恶意仓库、沙箱逃逸或自动审批 reviewer 的判断。实验记录与探针提供了环境说明和复现步骤。

保留 workspace-write，也能无人交互运行

如果依赖已经准备好，任务只需要在允许的工作区内改文件：

codex -a never exec --sandbox workspace-write \
  "Fix the failing tests. Run the relevant checks and report what changed."

exec 不启动交互式终端界面。workspace-write 规定文件系统边界，-a never 禁止请求审批，因此越出当前权限的命令不能在运行中申请提权。任务需要下载依赖或访问其他目录时，可能无法完成；这些访问条件要在启动前准备好。

我还让每种配置各做一次普通任务：创建内容为 print('workspace ok') 的 greeting.py，然后运行它。workspace-write 完成了，没有用到 Codex YOLO mode；YOLO 也完成了。read-only 下，agent 表示无法创建文件，没有调用工具。普通任务加上固定探针，共六次 CLI 调用。

六次 CLI 退出码全是 0，包括没有创建目标文件的 read-only 普通任务。流水线进入下一步前，还要检查目标文件和项目测试结果；正常退出本身不能证明任务达到了验收标准。

Codex auto mode 与已删除的 full-auto 命令

Codex auto mode 就是 OpenAI 文档里的 Auto 预设。按审批与安全文档的定义，它由 workspace-write 沙箱和 on-request 审批组成。工作区里的读文件、改代码、跑命令，Codex 直接做；在默认网络设置下，改工作区外的文件、运行需要联网的命令之前，它会先问你。

在有版本控制的目录里启动时，Codex 会把 Auto 作为推荐的默认值；信任该目录之前，它可能保持只读。会话中途可以用 /permissions 换预设，比如从 Auto 换成 Read Only。Auto 需要有人在终端前回应审批，无人值守运行应改用上一节的 workspace-write 命令。要显式指定 Auto，这样写：

codex --sandbox workspace-write --ask-for-approval on-request

旧教程常用的是一个简写：

codex exec --full-auto "fix the failing tests"

在 Codex CLI 0.100.0 中，交互式 codex --full-auto 的源码注释写作 -a on-request 加 --sandbox workspace-write，和 Auto 是同一组参数。在 codex exec 下，--full-auto 只设置沙箱，审批保持 exec 的默认值 never，所以旧的 exec 简写实际相当于 codex -a never exec --sandbox workspace-write。在我测试的版本中，这个参数在解析阶段就会报错，任务还没有开始：

$ codex --version
codex-cli 0.159.3

$ codex exec --full-auto --help
error: unexpected argument '--full-auto' found
# exit code: 2

2026 年 10 月 17 日补充核对时，我用 Codex CLI 0.163.0 重跑这条检查，报错相同；交互式的 codex --full-auto --help 也一样报错。OpenAI 当前的非交互运行文档说明，--full-auto 已不再支持。需要修改仓库的脚本应明确使用 --sandbox workspace-write；需要自动审批 review 时，改用 --approve-for-me，它已包含 workspace-write，不要再加 --sandbox。一些搜索结果描述的是过渡期的行为：Codex CLI 0.130.0 仍接受 --full-auto，只打印一条弃用警告。实际是否可用，要核对安装版本的参数解析结果。

迁移 Codex full auto 脚本时，先确定任务需要什么权限。如果脚本只需要修改仓库，把 codex exec --full-auto "..." 换成 codex -a never exec --sandbox workspace-write "..."。直接替换成 --yolo 会同时取消本地沙箱，放开的权限远不止修改仓库。

需要审批时，让自动 reviewer 判断

官方还提供了这个预设：

codex exec --approve-for-me \
  "Fix the failing tests and run the relevant checks."

它组合了 workspace-write、on-request 审批和自动 reviewer。CLI 文档列明它与显式 sandbox 参数、YOLO 冲突，应单独使用。

Auto-review检查符合条件、需要审批的操作。沙箱已经允许的命令不会经过这道 review；获批的提权请求可以跨出通常的边界。请求被拒绝后，agent 必须改用风险实质上更低的方案；找不到这样的方案时，应停下来询问用户。账户和组织策略也可能限制这个模式。

我只确认了 0.159.3 接受该参数，没有在这组实验里测试 reviewer 的决策。审批 review 与代码 review 的职责也不同：一个命令获准执行，并不能证明它生成的补丁正确、可以合并。

Orbi 的无人值守运行与合并流程

我做 Orbi，是想让编码任务一路完成 PR、评审和合并。在 GitHub Issue 中写清验收标准，加上 ai-ready，runner 就在单独的 worktree 中启动 Pi，推送任务分支、创建 PR。

runner 核对评审结论，拒绝评审后被外部改动的 PR head。基础分支前进且能无冲突合入时，它可以吸收更新、检查新的 head，无需再开评审会话。检查未完成时等待，失败时阻止合并。测试能覆盖什么，取决于仓库定义了哪些检查。

worktree 隔开检出目录，不能限制进程权限。自托管时，运行账户、凭据和网络访问要据此配置；评审管不到执行时已经读取的文件或发出的请求。

在 Cloud 发版

  1. 登录状态页，打开项目的“版本”区。只连了一个项目时，在页面底部展开“用量与设置 → 版本”。
  2. 在当前版本行点击“创建 Release 任务”。Cloud 会代建 GitHub 发版 Issue、加好标签，Orbi 执行门禁后打 tag、发布 GitHub Release。

原始记录：v0.5.60 Release、由 Cloud 创建的 Issue #1522。
