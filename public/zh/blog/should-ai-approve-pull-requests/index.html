GitHub Copilot、Claude Approvals、Cursor 和 CodeRabbit 现在都能在 PR 上提交批准评审，不过都要先有人打开开关、启用自动化，或者提交策略文件，才会开始批准。如果你是工程师或技术负责人，正在考虑要不要开这项功能，或者在想 agent 提的 PR 能不能不经人点批准就合并，这篇正好是写给你的。文章会交代我的立场、Orbi 替代批准按钮的合并门禁、我三个仓库 30 天的真实数据，以及哪些场景还是该留真人批准。

我是 Larry 🍀 Orbi，Orbi 的创始人。Orbi 是个开源交付引擎：给它一个打好标签的 GitHub Issue，它就让编程 agent Pi 写完改动，把 PR 交给独立的评审会话，检查通过直接合并，全程没人点 Approve。所以这件事和我有利益关系。

GitHub 的批准评审只记了哪个账号在哪个 commit 上点过头，不记查过什么，也不记改动在哪个 base 上测过。现在各家平台都允许 AI 来点这个按钮，顶上必需批准的名额。那 AI 到底该不该批准 PR？我的看法是：评审要独立于写代码的一方，但评审者不必是真人；人管好规则和最终验收就行，不用逐个 PR 去点批准。Orbi 完全不用 GitHub 批准：我的三个仓库把必需批准数都设成了 0，把门禁挪到了合并这一侧。

现在哪些工具能批准 PR

GitHub 在 2026 年 10 月 28 日的 Octoverse 2026 报告里写道："By September 2026, more than 40% of pull requests on GitHub started with an agent's first draft, up from 17% in March."（截至 2026 年 9 月，GitHub 上超过 40% 的 PR 初稿来自 agent，3 月时还是 17%。）下面四款工具里，只有两款写明了 AI 批准功能的发布日期：Copilot 是 2026 年 9 月 1 日，Claude Approvals 是 2026 年 11 月 23 日；我读的 Cursor 和 CodeRabbit 文档页都没标日期。四款都得先有人开启，或者写好策略文件。

GitHub 在 2026 年 9 月 1 日更新日志里写道："By default, Copilot will not approve pull requests."（默认不批准 PR。）打开之后，"When enabled, Copilot can submit an approval that counts toward the repository's required-approvals rule."（Copilot 提交的批准会计入仓库的必需批准规则。）这项功能面向对应套餐公测："This feature is available in public preview to GitHub Copilot Pro, Pro+, Max, Business, and Enterprise plans."（向上述套餐公测开放。）管理员还能 "choose which file paths Copilot is allowed to approve."（指定允许 Copilot 批准的文件路径。）一旦有新提交推上来，"If new commits are pushed after Copilot approves, its approval is dismissed just like a human reviewer's."（Copilot 的批准会和真人一样自动失效。）配置文档另外列出了企业级默认限制（"Organizations cannot enable Copilot approvals. This is the default."，默认禁止组织启用）、路径上限（"Up to 15 globs are supported."，最多支持 15 条 glob 规则），以及两个开关："Allow Copilot to approve pull requests" 和 "Allow Copilot approvals to count toward merge requirements"。

Anthropic 在 2026 年 11 月 23 日发布 Claude Ship 时推出了 Claude Approvals。按 Claude Ship 文档和 Approvals 文档的说法，"PR Steward and Claude Approvals are in public beta."（目前处于公测），并且 "Claude Ship is for organizations on Team and Enterprise plans."（面向 Team 和 Enterprise 组织）。启用靠 .claude/approvals.yml："Claude Approvals starts when a connected repository has a policy file on its default branch, and an admin can turn it off."（已连接仓库的默认分支只要有策略文件就会启动，管理员可以关掉。）也就是说，"anyone who can merge a policy file into the default branch can turn Approvals on."（任何能把策略文件合进默认分支的人都能把它打开。）席位规则里，"the author can fill a seat, so with seats: 1 nobody else has to look."（作者自己就能占满一个席位，配成 seats: 1 时别人可以完全不看。）落到分支规则上，"where a GitHub branch rule requires one approval, Claude's approving review can be that approval"（分支要求 1 个批准时，Claude 给出的批准评审就能顶上）。文档特意提醒："If you use GitHub auto-merge or a merge queue with a policy that doesn't require a person's approval, a change can merge without anyone acting."（策略不要求真人批准，同时开了 auto-merge 或 merge queue，没人动手，改动也会直接合进去。）

Cursor 的 Approval Agents 文档写着："PR Routing & Approval routes pull requests to the right reviewers and can approve low-risk changes."（负责把 PR 分给合适的评审人，并可以批准低风险改动。）入口设在 Cursor Automations 里："Automatically Approve PRs approves low-risk PRs after you configure approval criteria."（配好批准条件后会自动批准低风险 PR。）仓库里的 APPROVAL_POLICY.md 是可选项，agent 会自动发现并按里面的规则判断。文档里还提到："If Bugbot or Security Agents report findings that need human review, PR Routing & Approval will not approve the PR."（如果 Bugbot 或 Security Agents 报出需要人工复核的问题，它就不会批准。）

CodeRabbit 的 Automatic Approvals 文档写得很直接："Automatic Approvals is off by default."（默认关闭。）对应开关是 reviews.auto_approvals.enabled，"CodeRabbit approves only when every approval requirement is met."（只有满足全部批准条件时才会批准。）

一次批准记下了什么，又漏掉了什么

GitHub 的必需评审规则查的是账号身份。按 GitHub 文档："Pull request authors cannot approve their own pull requests."（PR 作者不能批准自己的 PR。）

一条批准评审只留下“另一个 GitHub 账号批准过某个 commit”，决定一次合并安不安全的关键信息却全没记：

  • 到底查了什么。逐条核对过验收标准，和扫一眼标题顺手点过，最后留下的绿勾一模一样。
  • diff 是对照哪个 base commit 看的。main 往前推进以后，早先给的批准依然算数，除非分支规则同时要求先同步到最新 base 再合并。
  • 这条批准现在还算不算数。GitHub 确实存了每条评审对应的 commit，但只要规则没开“推送新提交时使旧批准失效”，必需批准数里就可能还把旧提交上的批准算进去。

就算留着真人评审，一部分开源项目里 agent PR 实际得到的审查本来也不多。2026 年 1 月有一篇论文（arXiv 2601.13754），专门统计开源项目里由非仓库所有者提交、AI 共同编写的 PR，结论是："AI-co-authored PRs from non-owners receive the least, with approximately 80% merged without any explicit review."（非所有者提交的 AI 共同编写 PR 得到的审查最少，大约 80% 没有任何显式审查就合并了。）这项统计口径很窄（只覆盖开源仓库，只看非所有者提交的 AI 共同编写 PR），不能用来推断公司私有仓库的情况，也不能套到维护者自己提的 PR 上。它只说明这批 PR 实际得到的显式审查很少，并不代表随时间变化的趋势。

把点 Approve 的动作交给 AI，用的还是同一套机制：只认某个账号点过头，依然没把检查绑到最新的 base、通过的 CI 和最终要合并的那个 commit 上。

没有真人时的独立评审：Orbi 里的“独立”指什么

在 Orbi（main，commit d11224a5）里，评审在单独的进程里运行，用自己的提示词（prompts/prompt_review.md）另起全新会话，不接续实现阶段的上下文。它读的是 Issue 原文、可信评论、人在 PR 上留的反馈，以及一对冻结的 base/head SHA。

评审结束必须给出三种结论之一：pass、findings 或 blocked_on_human_decision。只要查出 Blocker 或 Major 级别的问题，就不能给 pass，结论里也会写明这次审的是哪个 head commit。输出要是解析不了，一律按报错处理，绝不当成 pass。

这种“独立”有两处比听上去弱：

  • 默认不会换用另一家厂商的模型。Orbi 支持单独配评审模型（review_pi_provider 和 review_pi_model），没配就复用实现阶段那个。我不会声称自己的仓库用了不同厂商的模型。
  • 评审员会在同一个会话里直接把 Blocker 和 Major 问题修掉、跑测试、推送提交，然后给出最终结论。这些在会话里顺手修好的改动，不会再进第二个评审会话。

这两个缺口靠后面的机制兜底。评审员推上去的任何 commit，后面都必须重新过 CI 和下一节的合并门禁。遇到它修不掉的问题，单子会贴上 ai-fix-needed 标签退回去重修，再走一轮流程。评审最多跑五轮，超过五轮就把 Issue 标成 ai-blocked 交给人拍板；同一个问题连着两轮出现，评审也会停下来问人。

Orbi 不点批准，合并前查什么

Orbi 从不提交 GitHub 批准评审，也不传 --admin，而是直接走合并流程，合并前强制查五道门禁：

  • 没有任何 CI 检查失败；检查还在跑，就等下一轮轮询再看。
  • PR 分支必须包含最新的 base。合并前 Orbi 先拉取最新 base；如果 PR 落后且合并没有冲突，Orbi 就把 base 合进 PR 分支、推送，把这个合并 commit 记成待落地的 head，等它跑完 CI。同一轮里刚推上去的 head 绝不直接合并。这次合并 base 不会触发第二次评审；一旦有冲突，或者其他人往分支推了新提交，Orbi 就把 PR 退回重新评审。
  • 真正合进去的 head 必须是刚验过的那个。Orbi 用 gh pr merge --match-head-commit <head> 来合并，上次检查完之后只要分支又动过，合并就直接报错退出，不会把没检查过的提交合进去。
  • 如果某项检查在 base 分支上本身就失败，Orbi 会暂停当前 PR，另开一张修 base 故障的 Issue。
  • 只要 Issue 上挂着 ai-blocked 标签，就算评审和 CI 全过，Orbi 也不会放行合并。

如果仓库的分支规则要求批准（required_approving_review_count >= 1），Orbi 不会自己批准自己，而是给 Issue 贴上 ai-awaiting-merge 标签，评论里写明需要人做什么，之后再重试。这条路径在我自己的仓库里还没跑过，因为我这边要求 0 个批准；上面写的是 Orbi 的设计行为，不是我实际跑过的记录。

有一类改动不走 PR：发版时，Orbi 会确认当前里程碑下没有未完成的工作，直接把递增版本号的 commit 推到 base 分支，等这个 commit 的 CI 全绿后再打 tag、发布。

30 天，零批准合并的 agent PR 数据

2026 年 11 月 27 日通过 GitHub API 核对，我的三个仓库都不要求批准评审：orbi-build/orbi-website 在 beta 和 main 上的 ruleset 要求走 PR，但 required_approving_review_count 是 0；orbi-build/orbi-cloud 的 ruleset 只拦删分支和强推，没有 pull-request 规则；orbi-build/orbi 没有覆盖 main 的 ruleset（include 列表为空），也没有经典分支保护。三个仓库查经典分支保护都返回 "Branch not protected"（404）。同样在 2026 年 11 月 27 日核对过，runner 的 PR 全由 GitHub App orbi-build（app/orbi-build）创建并合并。

读这组数据要注意四件事：

  • 这不是问题检出率。统计里混了 CI 重试，而评审员在自己会话里顺手修掉的问题留在第 1 轮里，没单独拆出来算。私有的 orbi-cloud 我也没留按原因拆分的记录。
  • 表格只统计了最终合并的 PR。
  • 这些数字只能说明评审加 CI 这条回路会把有问题的 PR 退回去重做，不能证明“没人批准就合并”一定安全。安全性靠的是合并门禁和发版阶段的验收。
  • orbi-cloud 是私有仓库，orbi 和 orbi-website 是公开的，所以你能点开核对的只有那 259 个公开 PR。

人还守在哪里

拿掉逐个 PR 点批准以后，人退到了两个位置：规则和发版验收。上游由人写 Issue、管分支和 CI 规则；碰到评审满五轮、问题重复出现或返回 blocked_on_human_decision，人再出面处理 ai-blocked 的单子。

下游拿 orbi-cloud 来说（具体过程我写过AI 代码评审是瓶颈吗？我们的 PR 卡在合并之后），推向生产依然由人把关：打完 tag 先部署到 beta，在 beta 上跑端到端新用户检查，我签字确认后再把晋升合进 main，最后生产部署还要人再点一次确认。验收挪到了跑起来的发布版本上，不再拆成一个个 PR 看 diff。

哪些情况应该保留人工批准

下面四种情况还是该留着真人批准：

  • 没有 CI 或测试薄弱的仓库。Orbi 不要求仓库至少配一项 CI 检查；不配 CI，PR 只凭评审就能合并。缺测试兜底的项目，不适合关掉人工批准。
  • 合完直接上生产、没有预发验收步骤的分支。少了 beta 验证和人工发版签字，撤掉逐 PR 批准就等于撤掉了验收门禁。
  • 策略和治理类文件。在 Claude Approvals 里，只要能把 .claude/approvals.yml 合进默认分支，就能打开 Approvals；改策略文件和 CI 规则的 PR，值得留人把关。
  • 合规要求或团队制度规定每个 PR 必须真人批准。保持 required_approving_review_count >= 1，交给 GitHub 强制拦截（Orbi 会把单子停在 ai-awaiting-merge 等人处理）。

如果你还是打算开 AI 自动批准

如果你还是打算保留必需批准规则，让 AI 工具顶上这个名额，开之前先核对五项设置：

  • 限制路径范围。Copilot 最多支持 15 条 path glob，把自动批准收在低风险文件里。
  • 别让作者一个人占满唯一席位。在 Claude Approvals 里，seats: 1 允许作者自己填满席位，别人完全不用看；另外，只要能把 .claude/approvals.yml 合进默认分支，谁都能打开 Approvals。
  • 让 CI 保持为必需检查，并要求合并前分支先同步最新 base，确保批准对应的是在最新 base 上测过的代码。
  • 推送新提交时让旧批准失效。新提交推上去后，Copilot 的批准会和真人一样自动失效；顺手核对一下规则，确认对真人批准也开了同样的设置。
  • 检查 auto-merge 和 merge queue。只要策略不要求真人批准，配合 auto-merge 或 merge queue，没人动手，改动也能直接合进去。

查一下你的分支到底要求什么

GitHub 的 ruleset 和经典分支保护用的是两套 API。查分支的 ruleset 是否要求批准：

gh api repos/OWNER/REPO/rules/branches/BRANCH \
  --jq '.[] | select(.type=="pull_request") | .parameters.required_approving_review_count'

2026 年 11 月 27 日实测：orbi-website 的 beta 输出 0；orbi-cloud 的 beta 没有任何输出（没有 pull_request 规则）；传不存在的分支名同样没输出，退出码也是 0；传不存在的仓库才返回 HTTP 404，退出码为 1。空输出代表“没有 ruleset 要求走 PR”，不代表“要求 0 个批准”，而且分支名拼错时结果完全一样。

上面那个接口只查 ruleset，经典分支保护要分开查：

gh api repos/OWNER/REPO/branches/BRANCH/protection \
  --jq '.required_pull_request_reviews.required_approving_review_count'

读取经典分支保护可能需要管理员权限。在我的三个分支上，这条命令都返回了 {"message":"Branch not protected",...,"status":"404"} 和 gh: Branch not protected (HTTP 404)，退出码 1。
