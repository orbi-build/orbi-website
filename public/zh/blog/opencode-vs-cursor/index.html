OpenCode vs Cursor 这个选择，一边是开源的终端编程 agent，一边是订阅制产品。OpenCode 由 anomalyco 开源，采用 MIT 许可（仓库原先在 sst/opencode），模型由你自己接；Cursor 是订阅制产品，有 AI 编辑器、云端 agent 和叫 agent 的命令行。这篇写给要把任务放进脚本、cron 或 CI 无人值守执行的开发者和团队负责人，关注的是无头运行（不开交互界面，直接在脚本里跑）。下面有两个命令行在密钥缺失或写错时的输出和退出码，有 OpenCode 跑四个小任务的结果，有两家截至 2026 年 11 月 16 日的价格，还有两家 GitHub App 在公开仓库开出的 PR（pull request，合并请求）数量。凭据是先遇到的区别：OpenCode 没有密钥也用免费模型跑了，Cursor 则停了下来。测试机器上没有 Cursor 账号，我没有注册，也没有付费，所以没有做登录后的 Cursor 运行；下文登录后的行为都引自 Cursor 文档。

OpenCode vs Cursor CLI：无头运行

安装和运行命令

下面是 Cursor 的安装和 print mode 命令，以及 OpenCode V2 的安装包和运行命令。两个安装都没有把命令放进我的 PATH，所以代码块里把两个目录都加上了。

curl https://cursor.com/install -fsS | bash
export PATH="$HOME/.local/bin:$PATH"
agent -p "Reply with exactly: hi"

npm install @opencode/cli
export PATH="$PWD/node_modules/.bin:$PATH"
opencode run --standalone "Reply with exactly: hi"

我在 2026 年 11 月 16 日把两者分别装进干净的 Linux HOME：Cursor CLI 是 2026.11.13-eacade1，OpenCode 是 2.3.0。我最初误装了 npm 包 opencode-ai，拿到的是 1.19.5；旧安装包安装的是 OpenCode 1，用 opencode --version 能看出装的是哪一个。下文所有 OpenCode 结果都用 V2，加了 --standalone，运行结束后不留下共享后台服务。

npm 那两行放到一个临时目录里跑：不带 -g 的 npm install 会把 node_modules 写在当前目录。用 npm 10.9.8 时，代码块照原样就能跑。用 npm 12.2.0 时，安装过程拦下了这个包的 postinstall 脚本，opencode 一直报 Error: @opencode/cli's postinstall script was not run.，补跑下面两行后才正常：

npm install-scripts approve @opencode/cli
npm rebuild @opencode/cli

Cursor 安装器把 agent 和 cursor-agent 放在 ~/.local/bin。它的 GitHub Actions 示例却把 $HOME/.cursor/bin 加入 PATH。我没有在 GitHub runner 上测试，使用时要先检查自己的 runner 上哪个目录存在。

OpenCode 没有密钥也能运行。即使提供了我的 DeepSeek 密钥，仍要固定模型或禁用免费模型，它才会选 DeepSeek。不带 -m 的每一行我都跑了三次：选出了模型的那几行，三次选的都是同一个模型；禁用免费模型且没有凭据的那一行，三次都报同一个错。OpenCode 的模型文档把回退行为写为 “falls back to the newest available supported model”。只在配置里写默认模型还不够，缺少它的密钥时仍会回退。

这些免费模型的数据条款不同。模型页写着，Big Pickle 在免费期间收集的数据可能用于改进模型；Iceman Free 的数据会保留并用于改进模型。CI 中的 secret 一旦缺失，代码就可能发给适用另一套数据条款的模型，运行仍然报成功。

我会禁用免费模型，并固定模型：

export OPENCODE_DISABLE_FREE_MODELS=1
opencode run --standalone -m deepseek/deepseek-flash "your prompt"

OPENCODE_DISABLE_FREE_MODELS=1 会隐藏免费模型。两行都加上后，缺少密钥和 DEEPSEEK_API_KEY 为空时，都报 Error: Model unavailable: deepseek/deepseek-flash，退出码 1；密钥错误时报 provider 的 Authentication Fails 错误，退出码 1；真实密钥则用 deepseek-flash 运行，退出码 0。把我用的 deepseek/deepseek-flash 换成你自己的模型。

无头运行不询问就能做什么

没有配置文件，也不加 --auto（这个参数会批准所有没被规则明确拒绝的权限请求）时，OpenCode 在项目内创建了文件、用 shell 命令向项目外写入，还用 curl 请求了 https://example.com，返回 HTTP 200。这些探测都用 -m deepseek/deepseek-flash 固定了模型。三项的退出码都是 0，没有询问，也没有拒绝操作。这符合默认权限：每个 agent 都从基础规则 { "action": "*", "resource": "*", "effect": "allow" } 开始，只有读取 .env 文件时设为 ask；文档还说，读取和编辑项目外的文件会 “proceed without a prompt”。所以默认策略放行了这三项探测；.env 读取规则和各 agent 内置的规则仍然适用。要限制其他操作，得自己加权限规则。

为了限制 shell 命令，我在 ~/.config/opencode/opencode.jsonc 加了这条规则：

{
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" }
  ]
}

文件里已有 permissions 数组的话，把这条规则加进数组。项目外写入的探测随后报告：This non-interactive run cannot ask the user for permission, so the request was rejected. Continue without this action. 文件没有生成，退出码却是 0。加 --auto 后就放行了。把 "effect" 改为 "deny"，加不加 --auto 都会拦住 shell 命令，符合这个参数保留显式 deny 规则的说明。

用 ask 规则跑下一节的第一个编程任务（修复单文件 bug）时，OpenCode 改了文件，但它调用 python3 -m unittest 时被拒绝了。我事后自己跑测试，通过了。这一次不算在下一节的 24 次运行里，那 24 次用的都是默认权限。

Cursor 登录后的这些行为，我没有实测。Cursor 文档说，print mode 不加 --force 也能编辑工作区文件；项目外写入、未经批准的 MCP 工具和网页抓取会被拒绝。shell 命令如果既不在允许列表里，也不能在已启用的沙箱里运行，同样会被拒绝。文档说，--force/--yolo 会放行所有操作，但 permissions.deny 和团队策略拦截的操作除外。团队管理员可以禁用无头模式，由客户端执行这项限制。

用哪款工具，都别把退出码 0 当成每一步都执行过的证明；脚本还得检查测试和 diff。

两家 GitHub App 在公开仓库开出的 PR

OpenCode 的 V1 GitHub 集成在收到 /opencode 或 /oc 后，用你的模型密钥在你的 Actions runner 上运行。它的 App 开出的 PR，作者是 opencode-agent[bot]。文档里的 use_github_token: true 模式不需要安装 App，所以这些 PR 没计入 App 数量；在终端里做完工作后由你自己开的 PR 也没计入。V2 文档索引没有 GitHub 页面，CLI 2.3.0 也没有 github 子命令。我没有在 V2 上测试这项集成。Cursor 的云端 agent开出的 PR，在这次观察中作者是 cursor[bot]。

我在 2026 年 11 月 16 日统计了 2026 年 11 月 2 日至 8 日 UTC 创建的公开 PR。数字反映查询时的状态，那时这些 PR 开出才 8 到 14 天，仍开着的之后还可能合并。两行不能拿来比较合并率。

我还读了 merged_by 字段。OpenCode App 的全部 119 个已合并 PR 中，87 个由用户账号合并，32 个由 bot 合并，后者包括 github-actions[bot] 合并的 28 个和 opencode-agent[bot] 合并的 4 个。我从 Cursor 已合并的 PR 中随机抽了 150 个，101 个由用户合并，49 个由 bot 合并，其中 43 个由 cursor[bot] 合并。这个字段不说明是谁请求了合并。

我把这些数字看作公开使用的证据：一小批仓库把 OpenCode 接进 Actions，另一批规模更大的仓库在用 Cursor，PR 大多是草稿。私有仓库和其他 PR 作者都不在统计里。

要统计自己的仓库：

gh api -X GET search/issues \
  -f q='is:pr repo:OWNER/REPO author:app/cursor is:merged created:2026-11-02..2026-11-08' \
  -q .total_count

把 OWNER/REPO、App slug（cursor 或 opencode-agent）和日期换掉；去掉 is:merged 就查总数。author:app/cursor 是 GitHub 搜索里对作者为 cursor[bot] 的 PR 的写法。-X GET 不能省：只带 -f 时，gh api 会改用 POST。需要先登录 GitHub CLI。我的测试在有匹配结果的仓库返回了 17 个已合并 PR；没有匹配结果时打印 0，退出码 0。仓库或 App 不存在时，报 gh: Validation Failed (HTTP 422)，退出码 1。搜索 API 每分钟允许 30 次请求。更完整的脚本还会统计其他状态。

OpenCode 和 Cursor 哪个好用，我按这几条选

  • 要带补全功能、按订阅付费的编辑器，选 Cursor。我没有上手比较过编辑器。
  • 要自己选 provider、在自己的机器或 CI runner 上跑，或者读源码，选 OpenCode。
  • 要无人值守地跑 Cursor，提供 CURSOR_API_KEY，并确保能访问 Cursor 的 API。云端 agent 和第三方模型从 Premium 开始提供。
  • 要无人值守地跑 OpenCode，用 -m 固定模型，设置 OPENCODE_DISABLE_FREE_MODELS=1，加权限规则，再自己验证结果。
  • 买席位前，我会在自己仓库的副本上，让两者用一周处理同样的真实任务票，再统计合并了哪些。

Orbi 能接哪部分工作

Orbi 不评审也不合并 OpenCode 或 Cursor 开出的 PR。它从打了 ai-ready 标签的 GitHub Issue 开始：先实现，再由独立会话评审，修复发现的问题，评审通过且 CI 全绿后合并。需要人工批准时，它会停下来。发版由人发起。

Orbi 没有编辑器，也没有终端聊天，唯一的任务入口是 GitHub Issue。它的引擎是 Pi，和 OpenCode 一样是开源终端 agent。Orbi 对比 Cursor 写了交接方式。想在编辑器或终端里和 agent 一起写代码，就不用考虑 Orbi。
