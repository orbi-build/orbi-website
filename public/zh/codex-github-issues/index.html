Codex · GitHub Issue · 打 tag 的发版

用 Codex 订阅处理 GitHub Issue，一路到发版

交付终点是发版。用 ChatGPT/Codex 订阅登录一次，给一张具体 Issue 打上 ai-ready；Orbi 写代码、开 PR、过独立评审、合并通过的那个 head，再打 tag 发布 GitHub Release。队列没人盯着，它自己走完。

登录

Codex OAuth，不需要 API key

Orbi 的 runner（Pi）用原生 openai-codex provider 走 OAuth 连 OpenAI。不使用 OPENAI_API_KEY，也不需要第二份 provider 文件，消耗的是你的 ChatGPT/Codex 订阅额度。下面几步照抄 provider 指南的 Codex OAuth 一节，按顺序做：

  1. 01 · 会话
    启动交互式 Pi 会话：pi
  2. 02 · 登录
    在 Pi 提示符中执行 /login codex

    在浏览器完成 Codex OAuth 授权。

  3. 03 · 检查
    回到 Pi 检查登录

    pi auth check --provider openai-codex --model gpt-5.6-luna --json 应报告 "status":"ready" 和 "authType":"oauth"。这条命令默认会刷新过期的 OAuth 凭据，共享终端里别带 --credentials。

  4. 04 · 配置
    检查成功后，再配置 Orbi

    如果存在 pi_providers，删掉并保持未设置；不要创建 openai-codex 条目。Pi 自己提供 catalog，Orbi 的 per-run agent 目录复用 Pi 原生 auth。

交付产线

一个标签，然后无人值守到发版

登录之后，流程就是 Orbi workflow 里那条产线；完整版在 Issue 到发版。

  1. 01 · 打标签
    给 Issue 打上 ai-ready

    这个标签把一张具体 Issue 放进交付队列。

  2. 02 · 实现
    Codex 在隔离 worktree 里实现

    改动在共享 checkout 之外完成，带着证据成为普通 GitHub PR。

  3. 03 · 评审
    另一个模型会话评审冻结的 diff

    最多 5 轮；评审方可以直接修复分支并推送。

  4. 04 · 合并
    只合并通过的那个 head

    CI 绿、head 未变、base 最新，否则重新评审。

  5. 05 · 发版
    打 tag 并发布 GitHub Release

    完成的 milestone 变成带 tag 的 GitHub Release。终点是发版，不是合并。

OpenAI 自己的做法

OpenAI 官方的集成写到评审和 PR 任务

OpenAI 官方文档记录了 Codex 与 GitHub 的集成：用 @codex review 让它评审代码、打开自动评审、用其他 @codex 评论把任务交给云端 agent——任务可以往分支推修复。这些文档覆盖的是评审和 PR 范围内的任务，发版不在其中。Orbi 用同一份订阅把剩下的路走完：合并门禁、打 tag、GitHub Release。
