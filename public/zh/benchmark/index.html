没见过的 bug

九个 Orbi 从没见过的 bug

都是 2026 年 8 月 10 日之后在上游合并的真实修复，Go、TypeScript、Python 各三个。每个的隐藏评分器就是维护者随修复一起写的测试。Orbi 看到的工单是改写过的，没有链接、编号，也没有修法提示。

容易改出回归的 bug

第一次真实修复就改坏过东西的 bug

三个真实 bug，上游第一次修复合并之后才发现改坏了别的东西：numpy（改坏了 ndarray 子类）、OpenTelemetry Collector（让 timeout 基本失效）、aiohttp（PONG 之后拒收合法的压缩帧）。工单只描述原始 bug，评分器两样都测。两套 harness 跑完的每一次都通过了；numpy 有一次 v15 因内存不足被停掉，未计分。人第一次修时犯的回归，不是这个 agent 会犯的那种。

调参集

更强的 harness 是怎么来的

三个 Orbi 合并过回归的 issue（pyinfra、chainloop、fedify）。我们一次改一条规则，把流程重跑了 96 次。这组数字是训练集成绩：harness 在这三个 issue 上调、又在同样三个 issue 上打分。

方法

每次运行怎么打分

  • 1
    真实流程，私有快照。

    每次运行都有一份自己的私有仓库，停在修复之前的那个 commit。没改过的 Orbi runner 认领 issue、实现、开 PR、评审、修改、合并。

  • 2
    隐藏的、校准过的评分器。

    任何一次运行计分之前，评分器必须在修复前的代码上判失败、在已知正确的修复上判通过。容易改出回归的题，还必须在上游第一次修复上判失败。评分时同时跑仓库自带的 lint、类型检查和全量测试。

  • 3
    碰不到答案。

    gh 和 git 外面套了一层，只放行这次运行自己的仓库，agent 查不到上游的修复。快照保留了被忽略却被跟踪的文件，以及 submodule 的内容。

局限

这些数字说明不了什么

  • n
    样本小，没有置信区间。

    没见过的 issue 九个，容易改出回归的 三 个，调参 issue 三个。很多格子只有 1 到 4 次。

  • 模型
    只测了一个实现模型。

    没见过的 bug 上，写修复的都是 deepseek-flash。其他模型只在调参集上试过。

  • 生产
    生产上的 Orbi 仍是原版 harness。

    更强的版本在一个分支上，不是 Orbi 的默认配置，原因就是上面这些结果。

  • 评分
    评分器只能抓到有人事先知道要测的问题。

    没见过的 bug 上，这个人是上游维护者。通过只说明维护者的测试和仓库测试都过了，不说明修复完美无缺。

复跑

自己跑一遍

任务、评分器、隔离包装和打分脚本都在 Orbi 仓库的 bench/oss-upstream（commit 7adcba9）。上游的测试没有拷进我们的仓库，heldout/fetch_hidden.sh 会从各自的修复 commit 取回来。一次只跑一个实例：单个任务就可能吃掉好几 G 内存。
