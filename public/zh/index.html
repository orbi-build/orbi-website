票进来之后

Runner 自己领。改完、再审一遍、合进 main。失败了还是这张 PR，不会另开一张。

  1. 01

    领取

    你给 Issue 打标。Runner 来领。没有第二套看板。

  2. 02

    实现

    单独的工作树。先写测试。提交只上任务分支。

  3. 03

    审查

    新进程，同一份 diff。能改就改。绝不推 main。

  4. 04

    合并

    main 要新。要能合。SHA 必须是刚审过的那个。

  5. 05

    接着干

    失败停在这张 PR。重启读 GitHub，不读聊天记录。

  6. 06

    发版

    一张发版 Issue：冻住底仓、核对范围、跑测试、打 tag。tag 从不强推。

聊天窗口交不了货

模型丢出一份 diff，审查、测试、合并还是你的事。窗口一关，活就没了。试一下够用。通宵把仓库推上去不够用。

难的是做完：测试要过，另一场看同一份改动，审过的提交进 main，机器重启了现场还在。

Orbi

  • Issue、PR、标签就是账本
  • 另一场审查，而且可以改

  • 下一拍还在这张 PR 上接着干

机器是你的。GitHub 只记账。

代码和模型留在你已经有的那台机器上。

它真正卡住的几件事

  • 只有一本账

    Issue、标签、PR、评论。没有影子库，也没有另一套工作区要对账。

  • 审查的人会改

    独立的一场。可以改代码、跑完全量、只推任务分支，再对修好的提交下结论。

  • 合进去的 SHA 对得上

    必须是刚审过的那个。底仓必须新。Runner 不自动解冲突。

  • 死了还能续

    进程被杀、测试挂了、本地提交没推出去——同一场、同一张 PR、下一拍继续。只有人必须拍板的才停。

  • 模型是你的

    本地 GPU 或自带密钥。兼容 OpenAI 接口。仓库不必离开你信的那台机器。

  • 测试就是门

    先写测试。跑全套。Python 运行时行和分支都要 100%。失败就停，没有退路。

活已经在 GitHub Issue 里，就在那儿跑。

Apache 2.0。自己托管。当前是 v0.2.0。接上你已经在付的模型。
