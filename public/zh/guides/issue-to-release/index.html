从 GitHub Issue 到打了 tag 的 Release

交付终点是发版，不是 PR。给一张具体 Issue 打上 ai-ready；Orbi 写代码、开 PR、独立评审，只合并审过的 head，再按 milestone 打 tag 并发布 GitHub Release。

交付产线

从 Issue 到发版的六步

流程来自 Orbi workflow。

  1. 01 · 打标签
    给 Issue 打上 ai-ready

    这个标签把一张 Issue 放进交付队列。

  2. 02 · 实现
    认领 Issue，在隔离 worktree 中实现

    Orbi 领取 Issue，在不干扰共享 checkout 的地方写代码。

  3. 03 · 开 PR
    开出 pull request

    实现结果带着证据成为普通 GitHub PR。

  4. 04 · 评审
    独立会话对照 Issue 验收项评审

    独立评审可以修复分支并重跑测试。

  5. 05 · 合并门禁
    CI 绿、head 未变、base 最新后才合并

    门禁保护刚刚审过的那个 head。

  6. 06 · 发版
    按 milestone 打 tag 并发布 Release

    发版流程把完成的 milestone 变成带 tag 的 GitHub Release。

先写清楚契约

写好一张 ai-ready Issue

写清一个运行结果，以及别人可以检查的验收项。不要写项目计划，也不要把无关愿望堆在一起：Issue 是实现和独立评审使用的契约。ai-ready Issue 的 12 个要素可以帮你补齐。在 Orbi Cloud 里也可以直接写需求：用一句话说想改什么，Orbi 读完仓库写出 Issue 草稿，你没说清的地方先问你。

如果结果无法检查，Orbi 就无法安全判断它是否完成。

FAQ

把 Issue 交出去前的几个问题

会合并没审过的代码吗？
不会。只合并独立评审通过的 head；请看合并门禁指南。

使用什么模型？
Pi 支持 OpenAI 兼容 API 或 Codex 订阅，不支持 Claude Code。

花多少钱？
自托管 Orbi 免费，模型费用由你承担；Cloud 价格见成本页。

开源吗？
是，协议为 AGPL-3.0。
