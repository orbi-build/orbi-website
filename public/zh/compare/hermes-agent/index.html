Orbi vs Hermes Agent

通用助理，还是软件交付产线。Hermes Agent 是 Nous Research 开源的常驻个人 agent：跨对话学习、运行定时任务、通过消息平台触达你。Orbi 是 GitHub 原生的软件工程 agent：把一个 Issue 推进到实现、独立审查和合并。两者都能在开发者要求时碰 GitHub，但产品围绕的工作不同。

按官方材料描述竞品

Hermes Agent 是什么

Hermes Agent 自称“由 Nous Research 打造的自我改进 AI agent”。官方仓库列出的能力包括持久记忆、跨 Session 搜索、技能创建与自我改进、定时自动化、多种终端后端和消息网关。仓库创建于 2025-07-22，采用 MIT 协议，作者标为 Nous Research。

来源：官方仓库（描述、创建日期、MIT 协议）；Hermes 官网（产品定位）——核实于 2026-09-07。

相关，但不是同一类

Hermes 与 OpenClaw：相邻的通用助理

Hermes Agent 与 OpenClaw 是两个独立的开源、自托管通用助理，在消息、记忆、自动化和 GitHub 工具方面有交集。本次查阅的官方材料没有把 Hermes 描述为 OpenClaw 的 fork 或关联项目。两者都不应被描述成 Orbi 的 Issue 到审查后合并交付闭环；后者是 Orbi 独有的产品边界。

来源：Hermes Agent 官方仓库与OpenClaw 官方网站（定位与项目身份）；Orbi 文档（交付闭环）——核实于 2026-09-07。

部署与能力边界

可部署在服务器上的通用助理，也有 GitHub 工具

Hermes 可以作为网关运行在你管理的机器上，通过 Telegram、Discord、Slack、WhatsApp、Signal 或 email 触达。README 明确给出 $5 VPS、GPU 集群和 serverless 后端等部署例子。它支持配置切换 provider，并包含 cron、记忆、技能和终端后端。

问题官方材料能确认什么官方材料没有确认什么
GitHub内置 GitHub skill 文档覆盖仓库检查、Issue、PR、代码审查和 issue-to-PR 工作流。没有文档证明它提供一个无人值守、自动领取、实现、测试、审查并合并的 GitHub Issue 队列产品闭环。
自托管CLI 和 gateway 可在操作者的机器（包括 VPS）上运行；终端后端包括 local、Docker、SSH 等。开源仓库不要求 Hermes 托管服务；服务器与凭证由操作者负责。
常驻工作gateway 对话与 cron 自动化可以无人值守运行，并向消息平台投递。常驻个人自动化不等于 Orbi 的 GitHub 原生交付状态机。

决定选择的差异

重心不同

Hermes 是把 GitHub 当作一个工具的广义助理；Orbi 是把队列、状态、证据和产出都放在 GitHub 对象里的软件交付系统。这不是高低判断，而是各自优化的工作流。

诚实的判断

该运行哪一个？

实际边界不是“谁能碰代码？”两者都能。问题是 GitHub 交付是产品的主要状态机，还是个人助理中的一项能力。

选 HERMES，如果你要

一个会与你一起成长的助理

  • 持久记忆、可复用技能和跨 Session 对话搜索
  • 一个网关处理消息、定时自动化和更广泛的工具
  • 自托管的通用 agent，任务需要时也能使用 GitHub

选 ORBI，如果你要

让 Issue 变成审查后的软件

  • GitHub Issue 就是队列，依赖关系和交付证据都在 GitHub
  • 独立审查可以在审查后的 commit 合并前修复分支
  • 可重复的软件交付闭环，而不是通用对话入口
