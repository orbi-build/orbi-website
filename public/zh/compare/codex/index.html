Orbi vs OpenAI Codex

软件工程目标相同，边界不同。Codex 是 OpenAI 的云端软件工程 agent：通过 ChatGPT、CLI 或 GitHub 发任务，在隔离的云沙箱里执行。Orbi 则把 GitHub Issue 变成你自己机器上的审查后 PR，并使用你选择的模型端点。本页把取舍讲清楚，不假装有一个工具适合所有人。

什么是 OpenAI Codex cloud

OpenAI 在 2025 年 5 月以 research preview 发布 Codex：一个可并行处理多个任务的云端软件工程 agent。每个任务都有独立的云沙箱，仓库会预载进去，产出可以是 pull request。Codex 的入口包括 ChatGPT、Codex CLI 和 GitHub 集成，使用 OpenAI 自研的 Codex 系列模型。

来源：OpenAI《Introducing Codex》发布公告、Codex 文档——核实于 2026-09-07。

跑在哪里

Codex 跑云端还是本地

Codex 跑云端还是本地，问的是 agent 在哪执行：OpenAI 托管的云端沙箱，还是你面前这台机器。云端路线从 ChatGPT 或 GitHub 起任务，在隔离的云端沙箱里预载仓库执行，本地什么都不用搭，几个任务并行也方便。本地路线是自己终端里的 Codex CLI：它直接在你的本地仓库上工作、调用机器上已经装好的工具，代码和凭据都留在原处——代价是机器要自己出，任务要自己发起，跑起来还得自己盯着。云端路线换走了什么，见下一节。

Orbi 是第三种：本地执行，按云端的方式交付。你写一个 GitHub Issue、打上 ai-ready 标签；Orbi 认领后在你机器的 Git worktree 里实现、跑测试、评审改动，最后开一个 PR 走普通合并——从 Issue 到合并全程无人值守，不用贴提示词，也不用守着运行。代码、密钥和运行证据留在你的基础设施上，模型端点由你选（BYOK）。Codex 指南里写了怎么配 ChatGPT/Codex 订阅来跑；不想自己运维 Runner，可以让 Orbi Cloud 在托管 Runner 上跑同一套 Issue 到合并的流程。

一句话选：要零搭建和托管并行，选云端；要仓库和凭据不出本机，选本地 CLI；要这个本地边界又不想守着运行，选 Orbi。

来源：OpenAI 的 Codex CLI 文档（终端、本地仓库、已装工具）和 Codex 文档；Orbi 文档——CLI 页核实于 2026-10-18，其余核实于 2026-09-07。

VENDOR 背刺风险

云端便利也会移动边界

云沙箱可以免去本地配置，让并行执行更方便。但这也意味着服务价格、模型供给、账号访问和仓库及任务上下文经过的基础设施由 vendor 控制。

风险Codex cloudOrbi 的取舍
涨价云端访问绑定 ChatGPT 套餐；Codex CLI/API 使用可能另行按 API 计费。套餐和用量政策可能变化。自托管需要自己的硬件；模型用量付给自选 provider，也可以使用provider 额度（如有）。
降级Codex 模型迭代、可用性、限额和限流由 OpenAI 决定。BYOK 支持任意 OpenAI 兼容端点，切换 provider 只需改配置。
审计 / 数据仓库会预载进 OpenAI 云沙箱来执行任务。代码、密钥、状态和运行证据留在你的基础设施。
账号访问ChatGPT、CLI、GitHub 集成和 OpenAI 账号访问都在链路中。运行自托管核心不需要 OpenAI 账号。

来源：OpenAI 发布公告、Codex 文档、Orbi文档——核实于 2026-09-07。这些是所有权取舍，不是对服务质量的判断。

决定选择的差异

Orbi 和 Codex 差在哪

有用的问题不是哪个 agent 普遍更好，而是你要一个开箱即用的云端执行面，还是一个模型和数据边界都由你控制的 GitHub 原生交付系统。

维度OrbiOpenAI Codex cloud
任务入口GitHub Issue + ai-ready 标签ChatGPT 侧边栏、CLI 或 GitHub 集成
运行位置自己的机器和 Git worktreeOpenAI 云沙箱，每个任务一个独立环境
状态GitHub Issues、labels、分支和 PROpenAI 服务中的任务与仓库上下文
模型BYOK，任意 OpenAI 兼容端点，包括provider 额度（如有）OpenAI Codex 系列模型
交付独立审查后，再按普通 PR merge任务产出可以包含 PR
成本自备硬件加自选模型用量；没有 $/session-hour云端需 ChatGPT 套餐；CLI/API 使用可能另行按 API 计费
可审计全链路可读、可审计vendor 服务与云基础设施

CODEX COST · 价格核对于 2026-10-17

用 Codex 要花多少钱

Codex 没有单独的售价。要么随 ChatGPT 套餐使用，要么用 API key 登录、按 token 付 API 费用。OpenAI 的 Codex 价格页列出的套餐如下（美元价）：

套餐价格包含的 Codex
Free$0/月简单编码任务；桌面 app 中可用 GPT-6 Luna（分批开放中）
Go$8/月轻量编码任务；桌面 app 中可用 GPT-6 Luna（分批开放中）
Plus$20/月网页、CLI、IDE 插件和 iOS 上的 Codex；GPT-6.1 Sol 与 GPT-6 Luna；自动代码审查、Slack 集成；可用 ChatGPT credits 追加用量
Pro$100、$200 或 $500/月包含 Plus 的全部内容；目前没有 5 小时限额，但可能有每周限额；$500 档可用 Ultrafast 模式
Business每人每月 $20（按年付，至少 2 人）；按月付 $25管理后台、SAML SSO 和 MFA；更大的云端虚拟机；可用 credits 追加用量
Enterprise 与 Edu联系销售Business 的功能，加上 SCIM、EKM、RBAC、审计日志和数据驻留控制
API key按 API token 计费CLI、SDK 和 IDE 插件；没有 GitHub 代码审查、Slack 等云端功能

套餐买的是一份用量额度，不是固定的任务数。按 OpenAI 的估算，Plus 和标准 Business 席位每 5 小时可以发 15–160 条本地消息（GPT-6.1 Sol），换成 GPT-6 Luna 是 350–3,000 条。云端任务消耗的额度可能更多，另外还可能有每周限额。OpenAI 也提醒，不要拿 API 单价去推算订阅里包含多少任务。

额度用完后，Plus 和 Pro 用户可以购买 ChatGPT credits（用量点数），采用灵活计费的 Business、Edu 和 Enterprise 工作区购买的是工作区 credits。标准速度下，GPT-6.1 Sol 每百万输入 token 扣 50 credits，缓存输入 2.5，输出 250。一个 credit 合多少美元因套餐而异，OpenAI 价格页没有给固定值。

当前额度以用量面板为准。来源：Codex 价格，核对于 2026-10-17。

用 API key 时 Codex 怎么计费

标准档、短上下文，每百万 token（来源：OpenAI API 价格）：

API 模型输入缓存输入（读缓存）输出
gpt-6.1-sol$2.00$0.10$10.00

gpt-6.1-sol 的单次输入超过 272K token 时，整次请求按长上下文价计费：输入 $4.00、缓存输入 $0.20、输出 $15.00（见模型页）。首次把提示写入缓存，按未缓存输入价的 1.25 倍计费（见提示缓存文档），gpt-6.1-sol 短上下文是每百万 $2.50。API 的 Fast 模式是标准价的两倍。

Orbi 把 GitHub Issue 做成经过评审的 PR，跑在编码 agent Pi 上。自托管时，它可以通过 Pi 的 openai-codex provider 使用你的 ChatGPT/Codex 订阅（见 Codex 指南），也可以填你自己的 key，接任意 OpenAI 兼容端点。我们自己的 Orbi 用的是 DeepSeek，不是 Codex；成本页列出了每个合并 PR 的实测花费。

诚实判断

什么时候该选哪一个

选 CODEX，如果你要

把云端执行当作顺手的默认选项

  • 你已经是 ChatGPT 用户，希望从对话入口发起软件任务
  • 你想要多个独立预载沙箱并行工作，不想运维 runner
  • 你接受 OpenAI 云端执行、OpenAI 模型政策以及 ChatGPT 套餐（适用时 CLI/API 另行计费）
读 Codex 文档 ↗

选 ORBI，如果你要

让仓库本身成为任务队列

  • GitHub Issue、label 和 PR 已经是工作流，不需要第二个 workspace
  • 需要 BYOK、provider 额度（如有）或任意 OpenAI 兼容端点
  • 代码、密钥、状态和 agent 行为必须留在本地且可审计

Orbi Cloud 托管运行这套 GitHub 交付流程；自托管则把 Runner 留在你自己的基础设施上。

按边界选择

正确的 agent，是你能接受其边界的那个

如果 ChatGPT 入口和托管云沙箱值得依赖 OpenAI，就选 Codex。如果 GitHub 就是队列，而本地所有权、模型选择和可审计性更重要，就选 Orbi。
