OpenCode vs Cursor is a choice between an open-source terminal agent and a subscription product. OpenCode is an MIT-licensed terminal coding agent from anomalyco (the repository formerly at sst/opencode) that uses whichever model provider you connect. Cursor is a subscription product with an AI editor, cloud agents and a terminal CLI called agent. This post is for developers and team leads who want to run either one unattended in scripts, cron or CI. Below are each CLI's output and exit codes when the key is missing or wrong, OpenCode's results on four small tasks, both price lists as of 16 November 2026, and counts of the pull requests (PRs) the two GitHub Apps opened in public repositories. Credentials are the first difference: OpenCode ran on a free model without a key; Cursor stopped. I have no Cursor account on the test machine and did not create or pay for one, so I made no logged-in Cursor run; authenticated behaviour below comes from Cursor's docs.

I'm Larry 🍀 Orbi, the creator of Orbi. Orbi takes GitHub Issues through implementation, separate review and merge using Pi, another open-source terminal agent; it overlaps with Cursor's cloud-agent half, so read the section on where Orbi fits with that in mind.

OpenCode vs Cursor CLI: running headless

The commands

The Cursor install and print-mode commands and OpenCode V2 package and run command are below. Neither install put its command on my PATH, so the block adds both directories.

curl https://cursor.com/install -fsS | bash
export PATH="$HOME/.local/bin:$PATH"
agent -p "Reply with exactly: hi"

npm install @opencode/cli
export PATH="$PWD/node_modules/.bin:$PATH"
opencode run --standalone "Reply with exactly: hi"

I installed both into clean Linux homes on 16 November 2026: Cursor CLI 2026.11.13-eacade1 and OpenCode 2.3.0. I mistakenly installed the npm package opencode-ai first and got 1.19.5; older packages install OpenCode 1, and opencode --version shows which one you have. All OpenCode results use V2 with --standalone, leaving no shared background service behind.

Run the npm lines in a scratch directory, since npm install without -g writes node_modules where you stand. With npm 10.9.8 the block worked as printed. With npm 12.2.0 the install blocked the package's postinstall script, and opencode printed Error: @opencode/cli's postinstall script was not run. until I ran these two lines:

npm install-scripts approve @opencode/cli
npm rebuild @opencode/cli

Cursor's installer placed agent and cursor-agent in ~/.local/bin. Its GitHub Actions snippet instead adds $HOME/.cursor/bin to PATH. I did not test on a GitHub runner; check which directory exists on yours.

OpenCode ran without a key. Even supplying my DeepSeek key did not select DeepSeek unless I pinned it or disabled free models. I ran each row without -m three times: the rows that picked a model picked the same one every time, and the row with free models disabled and no credentials gave the same error every time. OpenCode's model docs describe the fallback as "falls back to the newest available supported model". A configured default was insufficient when its key was missing.

Those free models have different data terms. The model page says Big Pickle's collected data may improve the model during its free period; Iceman Free's data is retained and used to improve it. A CI secret going missing can therefore send code to another model under different terms and still report success.

I'd disable free models and pin the model:

export OPENCODE_DISABLE_FREE_MODELS=1
opencode run --standalone -m deepseek/deepseek-flash "your prompt"

OPENCODE_DISABLE_FREE_MODELS=1 hides free models. With both lines in place, a missing key and an empty DEEPSEEK_API_KEY each gave Error: Model unavailable: deepseek/deepseek-flash and exit 1, a wrong key gave the provider's Authentication Fails error and exit 1, and the real key ran on deepseek-flash and exited 0. Replace deepseek/deepseek-flash, my model, with yours.

What a headless run may do without asking

With no config file and without --auto, the flag that approves permission requests no rule denies (the probes pinned -m deepseek/deepseek-flash), OpenCode created a project file, ran a shell command writing outside the project, and ran curl against https://example.com, returning HTTP 200. All three exited 0 and nothing was asked or rejected. That matches the permission defaults: every agent starts from a base rule of { "action": "*", "resource": "*", "effect": "allow" }, with ask only for reading .env files, and the docs add that reads and edits outside the project "proceed without a prompt". So the default policy allowed all three probes; the .env read rule and the rules built into each agent still apply. To restrict anything else, you add rules.

To restrict shell commands, I put this rule in ~/.config/opencode/opencode.jsonc:

{
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" }
  ]
}

If the file already has a permissions array, add the rule to it. The outside-write probe then reported: This non-interactive run cannot ask the user for permission, so the request was rejected. Continue without this action. The file was not written, yet the exit code was still 0. Adding --auto let it through. Changing "effect" to "deny" blocked the shell command with or without --auto, matching the flag's explicit-deny exception.

On the first coding task from the next section (fix a bug in one file), with the ask rule in place, OpenCode edited the file, but its python3 -m unittest calls were rejected. The tests passed when I ran them afterwards. That run is separate from the 24 in the next section, which all used the default permissions.

Cursor's authenticated behaviour here is untested. Cursor's docs say print mode edits workspace files without --force; outside writes and unapproved MCP tools or web fetches are rejected, as are shell commands neither allowlisted nor runnable in an enabled sandbox. The docs say --force/--yolo allows everything except permissions.deny and team-policy blocks. Team admins can disable headless mode, enforced by the client.

In either tool, exit 0 does not establish that every step ran; have your script check tests and the diff.

Console's Claude Opus 5.5 row lists, per million tokens: $4.00 input, $20.00 output, $0.20 cached read and $5.00 cached write. Go is optional, as is Console; I tested neither paid service.

Cursor's own-key docs describe editor settings and chat models only; Tab uses built-in models. Cursor's docs say your provider bills model usage, and requests still pass through Cursor's servers. I found no docs sentence saying whether own keys apply to the CLI. Its help lists bedrock, described as Configure AWS Bedrock usage for CLI; I did not test it.

I'd read Cursor's price as a seat and OpenCode's as my model bill. Which costs less depends on token usage. I have no Cursor usage data, so I give no cheaper-product verdict.

Cursor vs OpenCode on GitHub: the PRs their Apps opened

OpenCode's V1 GitHub integration runs on your Actions runner with your model key after /opencode or /oc. Its App's PR author is opencode-agent[bot]. The documented use_github_token: true mode requires no App installation, so those PRs fall outside this App count, as do PRs you open yourself after terminal work. The V2 docs index has no GitHub page, and CLI 2.3.0 has no github subcommand. I did not test this integration on V2. Cursor's cloud agents open PRs observed here as cursor[bot].

I counted public PRs created 2 to 8 November 2026 UTC on 16 November 2026. These are states at query time, when the PRs were 8 to 14 days old; open ones can still merge. The rows are not a merge-rate comparison.

Swipe horizontally to see all columns.

Author Opened Merged Closed unmerged Still open Draft now Repositories
opencode-agent[bot] 167 119 24 24 3 32
cursor[bot] 4,758 928 440 3,390 3,601 750

The populations differ in scale: 167 PRs across 32 repositories against 4,758 across 750. Who owns the repositories also matters. Among PRs created in October and counted the same way on 16 November, 2,709 of the 3,435 by opencode-agent[bot] were in anomalyco, the organisation that publishes OpenCode, including 2,357 in anomalyco/models.dev. Outside anomalyco, October had 726 opened and 530 merged. In the November week, anomalyco accounted for 37 of 167.

Draft now overlaps the state columns: Cursor's 3,601 flagged records include 363 closed unmerged and 36 merged PRs. I did not establish why merged records retained the flag, or the default at creation. Of all 4,758, 19.5% were merged; among the 1,157 not flagged draft, 892 (77.1%) were. Devin vs Cursor found a similar gap for October: 19.2% of all cursor[bot] PRs merged, 73.0% of those not flagged draft. The creation windows and observation dates differ, giving unequal follow-up periods.

I also read merged_by. Of the 119 merged OpenCode App PRs, user accounts merged 87 and bots merged 32, including 28 by github-actions[bot] and 4 by opencode-agent[bot]. Among 150 randomly sampled merged Cursor PRs, 101 were merged by users and 49 by bots, including 43 by cursor[bot]. The field does not say who requested the merge.

I take this as evidence of public usage: a small set of repositories wiring OpenCode into Actions, and a larger set with mostly draft Cursor PRs. It cannot tell me which agent's code gets accepted more often. Private repositories and other PR authors are absent.

To count your own:

gh api -X GET search/issues \
  -f q='is:pr repo:OWNER/REPO author:app/cursor is:merged created:2026-11-02..2026-11-08' \
  -q .total_count

Replace OWNER/REPO, the App slug (cursor or opencode-agent) and dates; drop is:merged for the total. author:app/cursor is how GitHub search names PRs whose author is cursor[bot]. Keep -X GET: with -f alone, gh api switches to POST. It needs GitHub CLI logged in. My tests returned 17 merged PRs in a repository with matches; no matches printed 0 and exited 0. A nonexistent repository or App produced gh: Validation Failed (HTTP 422) and exit 1. The search API allows 30 requests a minute. The fuller script counts the other states too.

Which one to choose, and what I'd check first

  • Choose Cursor for an editor with completions and a subscription bill. I have not compared the editors hands-on.
  • Choose OpenCode to pick your own provider, run on your own machine or CI runner, or read the source.
  • For unattended Cursor runs, supply CURSOR_API_KEY and access to Cursor's API. Cloud agents and third-party models start at Premium.
  • For unattended OpenCode runs, pin -m, set OPENCODE_DISABLE_FREE_MODELS=1, add permission rules and verify results yourself.
  • Before buying seats, I'd run the same real tickets through both on copies of my repository for a week and count what merged.

Where Orbi fits, and where it doesn't

Orbi does not review or merge PRs opened by OpenCode or Cursor. Its work starts with a GitHub Issue labelled ai-ready: it implements, has a separate session review, fixes findings, and merges when review passes and CI is green. It stops for required human approval. A release starts when a person requests it.

Orbi has no editor or terminal chat; its only intake is a GitHub Issue. Its engine is Pi, an open-source terminal agent like OpenCode. The Cursor comparison covers the handoff. Anyone wanting to pair with an agent in an editor or terminal should skip Orbi.
