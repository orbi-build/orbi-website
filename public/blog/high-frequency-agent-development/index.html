Agentic software development beyond one session

Orbi is an open-source system for agentic software development: it takes a GitHub Issue through implementation, review, merge and release. This article is for maintainers who already use coding agents and want delivery to keep moving between sessions. It gives three rules to adopt: recover only work you own, distinguish stale external state from a real change, and apply a new human decision before merging.

I'm Larry 🍀 Orbi, the creator of Orbi, and I use it to develop Orbi itself. Once I authorize a prepared task, Orbi starts the implementation session and, when the code is ready, an independent review session. The runner, Orbi's scheduler, saves progress, waits for checks and merges when the conditions hold; a separate release task publishes the version. I do not have to carry the task from one conversation to the next. Product decisions and required production approval remain mine.

Resume only work this deployment owns

On 18 November, Issue #2256 asked for a change to Orbi's own restart recovery. A runner looking for interrupted work could mistake another deployment's live delivery for its own abandoned one. Both deployments could then work on the same task branch.

The requested outcome was specific: resume an in-progress Issue only when this deployment has its own worktree and saved run state for it. A Git worktree is a separate checkout; Orbi keeps the task's files and execution state there. An in-progress label alone was insufficient evidence of ownership.

Orbi's delivery code records the base, run and worktree at claim time. When it resumes an existing worktree, it keeps that worktree's original branch.

The recovery rule can be written as an acceptance case for another project:

Given an in-progress task with no local execution state, leave it alone. Given the deployment's own saved work, continue that work. Skipping the first task must not hide another task that this deployment can resume.

The merged PR implements this ownership rule without introducing another ownership service. Writing "restart recovery is broken" would have left the agent to invent that rule. I need to put the policy in the Issue, with a trigger, an observable outcome and the boundary of the change.

Let the runner handle waiting

Another source of unnecessary work appeared when a task branch needed the latest base code. The runner could merge that base without conflicts and push successfully, yet a subsequent GitHub PR query still reported the old head commit. The branch ref and the PR view briefly disagreed.

Issue #2017 records the resulting mistake: Orbi interpreted the old PR view as a head change and sent work back through review. The push had succeeded; there was no new implementation problem for a model to solve.

PR #2019, merged on 30 October, made the distinction explicit. After confirming the pushed branch ref, the runner briefly rereads a PR view that still shows the pre-push head. If the view catches up, it uses the new state. If it never catches up, it refuses the merge. If it sees a third commit, that is an unexpected change, not the known stale result, and it fails immediately.

The current merge code keeps this wait bounded. After merging the base branch into the task branch and pushing, the runner waits until a later scheduler pass to check the new head's CI before merging the PR. A conflict-free merge of the base updates the recorded head without another model review; this is an explicit exception to re-reviewing a changed task branch.

The same separation applies to ordinary CI waiting. Orbi can save a clean review with the head commit and the Issue body the reviewer read. If those inputs still match, a later pass can check whether CI finished and attempt the merge without launching another review session.

A related change on 19 November, PR #2265, tells reviewers to use successful CI checks for the current head as verification evidence. Local tests still belong in reproducing a failure or checking a repair. The review instructions also tell the reviewer to return its verdict after pushing a fix, leaving subsequent CI waiting to the runner. This instruction change is outside the seven-day activity window below; I have no before-and-after runtime measurement for it.

Apply a changed decision before merging

A maintainer can change an earlier answer after review, while CI is running. The code may satisfy the decision the reviewer saw, while the maintainer has supplied a newer one.

Issue #2221 addressed that gap. The merge path did not consistently apply a new answer to a question Orbi had paused to ask, so it could continue with the older decision. PR #2229, merged on 17 November, added a final check for a newer, trusted answer that has not yet been carried out.

The merge gate reads that state immediately before its merge command. A pending answer stops the old result from merging and returns the delivery for repair. An answer already applied does not keep blocking it. If the answer history cannot be read, the gate holds the merge.

When Orbi pauses for a decision, it posts a question on the Issue. A maintainer with repository write access submits a new comment using the documented structured answer format. The runner checks that answer before merging; ordinary discussion comments do not enter this path. The resulting behavior is in v0.7.46.

Follow one task through release

The public trail for #2256 follows the work from claim to a published, verified package:

Version published v0.7.49 includes the Issue and PR in its verified release scope

The implementation session runs Pi, the coding agent. Orbi then starts a separate review process with fresh context. The reviewer reads the task and code, can fix findings on the same branch, and returns a verdict tied to a commit.

The release containing the restart fix, v0.7.49, was published on 18 November. Its record links release task #2263, identifies the release commit, lists the scope Issues as closed, and records the release commit's GitHub checks.

The release path does not start Pi. Program logic checks scope and release conditions, writes the version change, waits for the release commit's CI, then handles the tag and GitHub Release. A milestone with other open Issues does not enter release processing yet.

The Core PR query uses merge time; Releases use publication time, in the same window. The website also had 17 beta-to-main promotion PRs. They carry work already merged into beta, so I count them separately.

The website promotes beta to main for production without cutting a version for each batch. The Core publishes versioned Releases; a published Release does not establish that every hosted deployment or self-hosted installation has upgraded.

DORA's delivery metrics consider throughput alongside instability. These counts establish activity; they do not count useful features or measure productivity and deployment rework. I have separately measured waiting after merge.

What I still keep, and what I would copy first

I define the product outcome and authorize the work. I resolve decisions that require my authority, check behavior that needs a real user environment, and approve production where that approval is required. Orbi can automate the repeated implementation and delivery steps without making those product decisions disappear.

For another project, I would start with five questions:

  1. Can the next session locate the existing task, branch and work instead of starting a second attempt?
  2. Does an independent reviewer repair what it finds, or does somebody have to ferry its findings into another conversation?
  3. Can the runner wait for CI without spending another model session, while still checking the right commit?
  4. Can a new, authorized answer stop an obsolete decision immediately before merge?
  5. Does release have an explicit scope and verifiable conditions, separate from a model's completion message?
