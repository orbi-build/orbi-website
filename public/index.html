What actually happens to an Issue

This is the offer: an Issue becomes an implemented, independently reviewed, tested, merged PR, on the customer’s machine and model account.

  1. 01

    Claim

    You mark the Issue. The runner picks it up. Labels are the queue — no second board.

  2. 02

    Implement

    Isolated git worktree. Tests first. The change is committed on a task branch, never on main.

  3. 03

    Independent review

    A new process, a new transcript, the same diff. The reviewer can patch in-session. It only pushes the task branch.

  4. 04

    Merge

    Latest base, mergeable, exact reviewed SHA. Nothing else lands.

  5. 05

    Recover

    If it fails, it stays on that PR. Restart reads GitHub, not a local chat log.

  6. 06

    Release

    A release Issue freezes the base, checks scope, runs tests, tags, and publishes. No force-push of tags.

The chat window is not a delivery system

A coding agent writes a diff and hands the rest back to you. Review is a comment. Merge is you. Kill the process and the task is gone. That is fine for a spike. It is not how you ship a repository overnight.

The pain is not “AI cannot write code”. The pain is that engineering work has to finish: tests, an independent look at the same diff, a merge of the reviewed commit, and a scene you can recover when the box reboots.

Coding agent

  • State lives in a chat thread
  • One session writes and “reviews”
  • You merge, or you don’t
  • A dead process is a lost task

Orbi

  • GitHub Issue / PR / labels are the record
  • A second session reviews, and may fix
  • Only the reviewed head is allowed to land
  • Failure stays on the same PR; the next tick continues

Where it runs

Code and models stay on the box you already have. GitHub is only the record.

Why this is the product

  • GitHub is the only system of record

    Issues, labels, PRs, and comments. No shadow database, no agent workspace to reconcile.

  • Reviewer is a fixer

    Independent session. It can change code, re-run the suite, push the task branch, then verdict the new head.

  • Exact-head merge

    The merge matches the SHA that was reviewed. Base must be fresh. Conflicts are not auto-solved by the runner.

  • Recoverable by construction

    A killed runner, a failed test, an unpushed commit — same run, same PR, next tick. Blocked is only for things a human must decide.

  • Your machine, your model

    Local GPU or BYOK. OpenAI-compatible providers. The repo does not have to leave the box you already trust.

  • The test contract is the gate

    TDD. Full suite. 100% line and branch coverage on the Python runtime. Fail fast, no fallback path.

If the work already lives as GitHub Issues, run it there.
